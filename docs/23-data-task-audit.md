# 23 — 数据表与任务冗余审计

> 更新：2026-10-03。以可运行代码和生产库 schema 为准；容量和行数会变化。

## 结论

数据层按“原始事实 → 可重建投影 → 页面查询”收敛。普通战保留三层，CWL 保留两类原始档案加一张
投影；报名、公示和集结审计保持独立。没有把普通战、CWL 强行合并为泛型战争表。

| 领域 | 原始事实 | 可重建投影 / 缓存 | 结论 |
|---|---|---|---|
| 普通战 | `current_war_cache`（当前）、`war_history_cache`（已结束完整档案） | `member_war_facts` | 三者粒度不同，不能合并；历史每部落保留 45 场 |
| 都城突袭 | 官方周末赛季响应 | `capital_raid_status_cache`（开启状态）、`capital_raid_member_results`（成员事实） | 状态提醒和结束后贡献统计用途不同，不能互相替代 |
| CWL 战斗 | `cwl_live_group_cache`（赛程目录）、`cwl_live_war_cache`（逐场详情） | `league_results` | 分组和单场是一对多；成绩表保留为快速月度投影 |
| CWL 运营 | `registrations`、`league_teams`、`cwl_roster_snapshots`、`cwl_assembly_cache` | 无 | 分别表示报名、编排、公示和到位审计，不能互代 |
| 成员贡献 | 都城、竞赛各自事实表 | 页面聚合 | 时间粒度/来源不同，不应做泛型 JSON 表 |

## 普通战：已消除的重叠

过去 `war_results`、`member_war_facts` 和 `member_combat_stats_cache` 在普通战统计上职责重叠。
当前唯一写入链路为：

```text
官方 currentwar 或完整历史回填
  -> war_history_cache
  -> member_war_facts(metric_version=2)
  -> 部落战 API / 成员 API 实时批量聚合
```

- 两张旧投影表已在 2026-10-03 经 COS 备份、414 场结束战争均具 `metric_version=2` 事实、
  接口核验后物理删除。
- 新 schema、调度器、API 和脚本均不再依赖它们；若未来需要恢复，只能从 COS SQLite 快照恢复，
  不得重新引入第三方汇总直写。

API 不扫描历史 JSON：部落战页按 `(clan_tag, end_time)` 索引查询玩家事实；成员页按
`(player_tag, end_time)` 查询事实。历史档案存在的目的是真实可追溯和可重建，而不是请求路径解析。

## CWL：有意保留的有限重复

- `league_teams` 与原始分组都含队伍名称/标签：前者是编排权威快照，后者是抓取时自描述上下文；
  该少量复制防止历史页面依赖未来配置。
- `league_results` 与逐场档案同存：前者是确定性月度投影，服务下月编排和滚动查询；原始档案可重建它。
- `cwl_roster_snapshots` 与 `cwl_assembly_cache` 均关联名单：前者不可变公示版本，后者记录某个时点
  的现实到位情况和冻结结果，不能合表。

完整性不是“分组 state 已结束”的同义词。只有分组目录的所有 `war_tag` 都已有可解析最终战争，
才将 `raw_status` 标为 `complete` 并写月度投影。历史补档不得以第三方汇总数字绕过这一链路。

## 任务边界

| 任务 | 可写入 | 不可做 |
|---|---|---|
| `current_wars` | 当前状态、最终普通战档案和玩家事实 | 失败时清空上次快照；写任何旧聚合表 |
| `cwl_live` | 当前月 CWL 分组/单场原始档案 | 写未完成的 `league_results` |
| `cwl` | 从完整本地档案重建 `league_results` | 外部聚合 API 直写成绩 |
| `member_combat_stats` | 升级后旧战争的事实物化 | 写旧成员摘要缓存 |
| `capital_raid_status` | 最近周末各部落开启状态 | 写成员贡献事实；已开启后继续高频拉取 |
| `cwl_assembly` | 集结检查与冻结 | 修改已冻结的 `roster_snapshot_id` |

调度间共享数据时，以事实层为边界；不允许一个任务以便捷为由跳过完整性检查或直接改另一领域的表。

## 新表准入规则

只有下列任一项不同才建新表：唯一键/时间粒度、权威来源、可变性或历史保留规则、一对多关系、
访问性能已通过测量证明需要投影。相同实体与粒度的新展示字段优先扩展现有事实或投影，避免再造
“功能一张表”。每张新增投影必须同时写明：原始来源、重建命令、消费者、保留期和删除条件。

`sync_job_runs` 与 `external_request_events` 是 M0 可观测性所需的短期运行明细，不属于业务事实或
业务投影：前者记录每轮调度任务，后者记录该轮外部请求的来源、操作、结果和耗时。它们默认保留
30 天，过期可直接清理且无需重建；唯一消费者是只读诊断报告和后续容量基线分析。观测写入失败
不得影响业务任务，表中不保存凭证、请求头或响应正文。
