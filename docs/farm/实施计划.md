# 互刷联盟系统分阶段实施计划

> 状态：F0–F6 核心能力完成；F7 处于生产只读灰度；新增 F8 上线加固，完成后再开放登记
> 日期：2026-10-22
> 依赖：[互刷系统设计](./互刷系统设计.md)
> 阶段编号：使用 `F0–F8`，避免与多用户/多联盟计划的 `M0–M9` 混淆

## 1. 计划目标

本计划用于把已经确认的互刷联盟业务规则，分阶段落地为可验证、可暂停、可回滚的小程序功能，最终形成以下闭环：

```text
独立账号登录
  ↓
账号与互刷部落归属
  ↓
管理员建立统一场次
  ↓
成员单个或一键登记
  ↓
后端从 COC API 识别对手
  ↓
内部匹配自动判定输赢并结算积分
  ↓
匹配失败积分不变
  ↓
创建者可审计、撤销和恢复
```

每个阶段必须独立开发、测试、提交和验收。进入下一阶段前，需要当前阶段验收通过，并由用户明确授权继续；本文档本身不代表已开始修改功能代码或生产数据。

## 2. 实施原则

### 2.1 安全边界

- 互刷账号密码登录与微信登录完全隔离；
- 微信 JWT 不能访问互刷私有接口，互刷 JWT 不能访问微信用户私有接口；
- COC API Token 只留在后端环境变量中；
- 密码只保存强哈希，禁止明文、可逆加密或日志输出；
- 所有成员数据范围和角色权限由后端校验，前端隐藏按钮不能代替授权；
- 数据库迁移只做向前兼容的增量变更，不删除现有表和字段；
- 互刷积分、匹配和撤销必须可追踪、可对账，禁止直接覆盖历史事实。

### 2.2 与现有功能隔离

- 新系统使用 `/api/farm-system` 接口前缀；
- 新系统不改变现有 `/api/clan/farm-config` 和 `/api/alliances/{alliance_id}/farm-config`；
- 新系统不把 `farm_stats` 当作匹配或积分事实表；
- 新系统不把微信多联盟中的 `alliance_id` 当作互刷登录账号；
- 新系统复用 `CocApiClient.get_current_war()`，不复制第二套官方 API 客户端；
- 普通读取接口不调用 COC API，只有用户主动执行“登记”时才允许触发外部请求。

### 2.3 上线控制

计划引入两个独立开关：

| 开关 | 默认值 | 作用 |
|---|---:|---|
| `FARM_SYSTEM_ENABLED` | `false` | 控制互刷登录页、首页和管理页是否开放 |
| `FARM_SYSTEM_REGISTRATION_ENABLED` | `false` | 控制是否允许调用 COC API 登记和结算积分 |

前几个阶段即使代码部署到生产，也保持开关关闭。数据库表可以保留，不通过删表回滚。

## 4. F0：真实数据验证与技术基线

> 当前状态（2026-10-11）：已从现有缓存核对 8 个互刷部落，并通过官方 API 双向验证两组
> 内部匹配；时间字段、普通战争识别和对手标签均稳定。配置 `#YCOC` 被官方返回为 `#YC0C`，
> 已确认后续必须使用 `O → 0` 的 COC 比较键。运营已确认统一时间是“开始搜战时间”，固定映射
> 官方 `preparationStartTime`；第一版误差窗口为 2700 秒。详见 [F0 真实数据验证记录](./F0-真实数据验证记录.md)。

### 4.1 目标

在建表和写业务代码前，用真实互刷战争样本确认 COC 官方字段与业务“统一开战时间”的对应关系，避免把错误时间语义固化到数据库和匹配算法中。

### 4.2 实施范围

- 只读检查已有 `CocApiClient.get_current_war()` 和当前战争标准化模型；
- 选择至少一轮真实互刷样本，记录已脱敏的：
  - 管理员手工设置的业务时间；
  - 官方 `state`；
  - `preparationStartTime`；
  - `startTime`；
  - `endTime`；
  - 本方和对手标签；
- 在搜索完成、准备日、战斗日三个时间点验证 `currentwar` 可用性；
- 验证战争日志私密和公开部落的返回差异；
- 测量单个 `currentwar` 请求的正常、慢请求和失败耗时；
- 确认业务时间对应官方哪个字段，并确定初始误差窗口；
- 固化可用于测试的脱敏 COC JSON 夹具。

### 4.3 交付物

- 一份真实样本验证记录；
- 时间字段映射结论；
- 初始误差窗口配置建议；
- `preparation`、`inWar`、`notInWar`、私密/失败等测试夹具；
- 一键登记采用前端串行还是服务端批次的初步延迟依据。

### 4.4 验收标准

- 能明确回答业务时间对应 `preparationStartTime` 还是 `startTime`；
- 同一内部匹配双方返回的对手标签和战争时间一致；
- 可以可靠区分尚未匹配、时间不符、权限/网络失败和有效战争；
- 测试夹具不包含令牌、授权头或不必要的用户隐私数据；
- 本阶段不写生产数据库、不改变页面和调度行为。

### 4.5 暂停条件

如果真实样本无法稳定取得对手标签或时间字段无法映射，不进入 F4。可以继续完成 F1–F3 的离线底座，但登记按钮保持禁用。

## 5. F1：数据库与独立认证底座

> 当前状态（2026-10-22）：已完成独立认证、增量表结构、受控账号运维入口和测试；
> F8 工作分支互刷及同步队列目标测试 75 项通过。系统入口已对白名单账号开放，登记功能仍关闭。
> 账号统一使用邮箱登录。

### 5.1 目标

建立互刷系统最小数据基础和独立认证边界，不开放实际登记功能。

### 5.2 数据库变更

第一批只增加：

- `farm_auth_accounts`；
- `farm_clans`；
- `farm_audit_logs`。

迁移要求：

- 统一放在 `shared/db`；
- 重复启动和重复迁移不产生重复表、索引或账号；
- 现有数据不迁移、不修改；
- 唯一登录邮箱、唯一部落标签、合法角色和状态由数据库约束辅助保证；
- 只允许一个有效创建者账号；
- 新部落积分默认 `0`。

### 5.3 后端范围

建议新建独立领域模块：

```text
modules/farm_system/
  auth.py
  models.py
  repository.py
  service.py
```

建议新增路由模块：

```text

```

首批接口：

```text
POST /api/farm-system/auth/login
POST /api/farm-system/auth/logout
POST /api/farm-system/auth/change-password
GET  /api/farm-system/me
```

认证要求：

- 使用独立 JWT 受众 `aud=farm-system`；
- 令牌包含 `farm_account_id`、`role` 和 `token_version`；
- 登录错误不暴露账号是否存在；
- 登录失败有基础限流；
- 停用账号或递增 `token_version` 后，旧令牌失效；
- 使用 Python 标准库 `hashlib.scrypt` 和随机盐，编码为可升级的 `scrypt-v1` 格式；
- 不创建公开注册接口。

### 5.4 运维入口

新增受控命令或脚本，用于：

- 初始化唯一创建者账号；
- 创建成员或管理员账号；
- 生成密码哈希；
- 停用账号；
- 重置密码并递增 `token_version`。

第一版可以由运营者直接操作数据库，但必须通过该脚本生成哈希和写审计，禁止手工写入明文密码。

### 5.5 测试

- 迁移幂等测试；
- 登录邮箱规范化、格式和唯一性测试；
- 密码正确、错误、停用账号测试；
- 微信 JWT 访问互刷接口被拒绝；
- 互刷 JWT 访问微信私有接口被拒绝；
- 角色枚举和唯一创建者约束测试；
- 重置密码后旧令牌失效测试；
- 日志和响应不包含密码哈希、原始密码或令牌。

### 5.6 验收门槛

- 可以通过受控脚本建立创建者和测试账号；
- 独立登录和退出闭环成功；
- 微信登录状态与互刷登录状态互不影响；
- 所有目标认证测试通过；
- `FARM_SYSTEM_ENABLED=false` 时用户仍只能看到当前占位入口。

### 5.7 回滚

- 关闭 `FARM_SYSTEM_ENABLED`；
- 移除或禁用新路由注册；
- 保留新增空表和迁移版本，不执行降级删表；
- 现有微信认证和页面不需要回滚。

## 6. F2：账号与部落归属管理

> 当前状态（2026-10-22）：后端、独立登录页和管理页已实现；生产现有 2 个启用账号和 9 个启用部落，
> 系统入口对白名单账号 ID 1、2 开放，登记开关仍关闭。F8 工作分支已接通新标签受控同步、状态轮询
> 和验证成功后绑定，尚待部署验收。

### 6.1 目标

让创建者和管理员能够查看账号，并设置每个账号包含哪些互刷部落，同时保证部落唯一归属和历史连续性。

### 6.2 后端范围

新增或完成：

```text
GET   /api/farm-system/admin/accounts
POST  /api/farm-system/admin/accounts
PATCH /api/farm-system/admin/accounts/{account_id}
GET   /api/farm-system/clans/{clan_tag}/detail
GET   /api/farm-system/admin/clans
POST  /api/farm-system/admin/clans
PATCH /api/farm-system/admin/clans/{clan_tag}
POST  /api/farm-system/admin/clans/{clan_tag}/transfer
```

核心规则：

- 添加部落时从受控同步任务写入的官方部落资料缓存确认标签和名称，禁止在 HTTP 请求路径直连 COC；
- 标签统一去空格、转大写并补齐 `#`；
- 一个部落只能绑定一个账号；
- 管理员和创建者可以新增、停用和转移部落；
- 转移只改变当前归属，积分不归零、历史不迁移、不复制；
- 停用账号或部落只改变状态，不删除事实；
- 创建者才能设置管理员角色；唯一创建者的初始化、停用或转移暂只允许受控运维入口，避免页面误操作锁死管理权限；
- 第一版只有一个创建者。
- 部落详情按“基本信息 / 互刷信息 / 对手部落”返回：基本信息和本轮互刷对手资料来自官方资料缓存，
  互刷信息来自当前场次快照；详情读取与资料刷新使用两个独立接口，刷新接口只将缺失或已满 6 小时的
  `clan_profile` 提交到全局去重队列，不触发当前战争、积分或匹配刷新；普通成员只能读取自己账号绑定的
  部落，管理员和创建者可读取全部部落。

### 6.3 前端范围

新增互刷独立登录页和分层管理页面：

- 使用独立存储键 `farm_token`；
- 把“管理 → 互刷联盟系统”占位按钮改为进入互刷登录/首页；
- `admin.vue` 只作为全联盟管理首页，使用与普通联盟管理页一致的纵向卡片菜单进入场次、部落和账号独立页；
- 管理首页不再保留范围说明、功能选择标题或重复的功能介绍区；
- 场次、部落和账号的具体操作不在管理首页直接展开。
- 部落管理列表、普通账号首页及账号专属互刷部落页中的部落卡片都进入统一部落详情页；
- 账号列表不再单独放置“编辑”按钮；点击账号卡片主体直接进入账号专属互刷部落页，展示该账号全部部落的积分和状态，并允许停用或重新启用部落；
- 列表和管理菜单首次进入显示加载状态，从详情页返回时保留旧内容与滚动位置并静默刷新，避免整页闪烁；
- 统一详情页的基本信息使用一张完整卡片展示部落名称、标签、启用状态、公告、位置、人数、等级、加入方式
  和缓存更新时间，不再展示与互刷信息重复的当前普通部落战卡片；互刷信息展示积分、当前场次、登记状态、
  互刷对手及预定胜负；第三部分展示当前互刷对手的名称、标签和公告等官方缓存资料；
  页面先读取缓存，再为本方和本轮互刷对手提交按需资料任务；仅当缓存缺失或已满 6 小时才入队，前端静默
  轮询并只更新基本资料。任务通过 Worker 调用 COC，不在 HTTP 请求中直连；普通战争、积分、场次、匹配和
  胜负不随页面浏览刷新。第三部分不回退展示普通部落战对手；资料尚未完成时明确显示“暂未同步公告”。

## 7. F3：场次与成员首页

> 当前状态（2026-10-11）：统一场次、参与部落快照、成员首页和禁用的登记骨架已实现；
> 目标测试与小程序生产构建通过。场次时间固定为“开始搜战时间”，`business_time_kind` 只允许
> `preparation_start`。

### 7.1 目标

建立“一个当前场次”和参与部落快照，并让成员看到统一时间、自己的部落、积分和登记状态；本阶段登记按钮仍不调用 COC API。

### 7.2 数据库变更

新增：

- `farm_rounds`；
- `farm_round_clans`。

约束与事务：

- 最多一个未结束、未取消的当前场次；

- 保存部落标签、名称、账号归属和 `score_before` 快照；

## 8. F4：单部落登记与自动积分

> 当前状态（2026-10-11）：表结构、纯评分、单部落登记、幂等并发保护、原子积分和独立功能开关
> 已实现；统一时间固定校验官方 `preparationStartTime`，第一版误差窗口为 2700 秒；真实灰度尚未开始。

### 8.1 目标

完成第一版最关键的单部落登记闭环：获取官方对手、判断内部匹配、计算预定输赢、原子写入双方结果和积分。

### 8.2 数据库变更

新增：

- `farm_matches`；
- `farm_score_ledger`；
- `farm_registration_attempts`。

核心唯一约束：

- `(round_id, clan_id)` 最多一个最终结果；
- `(round_id, pair_key)` 最多一条有效内部匹配；
- 同一匹配同一部落只能有一笔基础胜负流水；
- 平分随机结果和随机审计值只保存一次；
- 当前积分、流水前后余额和部落物化积分必须一致。

### 8.3 领域服务

建议拆分纯规则与 I/O：

```text
modules/farm_system/scoring.py       # 纯函数：比较积分、决定胜负
modules/farm_system/registration.py  # 编排：权限、COC I/O、事务
modules/farm_system/repository.py    # 查询、唯一约束和原子写入
```

纯评分函数输入：

- 双方部落 ID；
- 双方 `score_before`；
- 可注入随机源。

纯评分函数输出：

- 胜方和负方；
- 是否使用平分随机；
- 双方积分变化。

### 8.4 登记接口

```text
POST /api/farm-system/rounds/{round_id}/clans/{clan_tag}/register
```

处理顺序：

1. 验证互刷令牌、场次和部落归属；
2. 检查是否已有最终结果，有则直接返回；
3. 调用 `CocApiClient.get_current_war()`；
4. 标准化本方、对手、状态和时间；
5. 拒绝 CWL、错误状态和时间不符战争；
6. 对手不在本轮快照时写 `match_failed`，积分不变；
7. 对手在快照中时建立规范化 `pair_key`；
8. 在一个数据库事务内锁定或重查双方结果；
9. 比较积分快照，平分时随机一次；
10. 写匹配、双方结果、两笔流水、部落当前积分和审计；
11. 首次最终登记同时锁定场次时间；
12. 返回双方一致的最终结果。

### 8.5 状态与重试

| 状态 | 是否最终 | 是否允许成员重试 | 是否改变积分 |
|---|---:|---:|---:|
| `not_in_war` | 否 | 是 | 否 |
| `war_mismatch` | 否 | 是 | 否 |
| `fetch_failed` | 否 | 是 | 否 |
| `internal_matched` | 是 | 否 | 是 |
| `match_failed` | 是 | 否 | 否 |

### 8.6 测试重点

- 低积分胜、高积分负；
- 同积分随机源可注入，结果稳定；
- 刷新和重复请求不重新随机；
- 非内部对手匹配失败且积分不变；
- `notInWar`、CWL、时间不符和 API 异常不改变积分；
- A 登记后 B 自动拥有相反结果；
- B 再登记直接复用结果；
- A、B 并发登记只生成一条匹配；
- 写第二笔流水失败时整笔事务回滚；
- 成员无法登记其他账号部落；
- 场次时间在首次最终登记后锁定；
- 登记尝试记录不包含官方授权信息。

### 8.7 验收门槛

## 10. F6：撤销、审计与运维工具

> 当前状态（2026-10-11）：创建者撤销匹配、整场原子取消、密码重置、审计记录和只读对账命令

### 10.1 目标

### 10.2 创建者能力

```text

```

- 双方部落积分在同一事务中恢复；
- 撤销整场逐项反向冲销已结算匹配；

- 重置密码递增 `token_version`，使所有旧令牌失效。

### 10.3 对账与诊断

新增只读诊断命令：

- 比较 `farm_clans.score` 与积分流水汇总；
- 检查每条内部匹配是否有双方结果和两笔流水；
- 检查同一部落同一场次是否存在多个最终结果；
- 检查已撤销流水是否完整成对；
- 检查场次完成数量与参与快照一致；
- 输出异常 ID，不自动修改生产数据。

修复工具必须：

- 默认 dry-run；
- 显示精确影响对象；
- 显式 `--apply --yes` 才写入；
- 写入前创建一致性备份；
- 写审计日志；
- 不直接删除积分流水。

### 10.4 可观测性

记录但不泄露敏感信息：

- 登录成功/失败数量；
- 登记请求量、成功率和耗时；
- COC `currentwar` 状态和错误类别；
- 内部匹配、匹配失败和可重试错误数量；
- 一键登记批次耗时；
- 唯一约束冲突和事务回滚；
- 积分对账异常；
- 撤销和密码重置操作。

### 10.5 测试与验收

- 撤销后双方积分准确恢复；
- 原匹配和流水仍然可追踪；
- 重复撤销不会重复恢复积分；
- 管理员和成员不能撤销；
- 整场撤销不会产生半完成状态；
- 密码重置后全部旧令牌失效；
- 对账命令能识别构造的积分、匹配和流水不一致；
- 备份、dry-run 和审计流程通过。

### 10.6 回滚

- 隐藏创建者撤销 UI，但保留只读审计和对账；
- 已执行撤销不通过删除反向流水回退；

## 15. F8：生产登记闭环与运营加固

> 当前状态（2026-10-24）：15.2 的四项 P0 代码已经部署；唯一创建者已初始化。生产登记开关已在
> 创建者确认后打开，首场场次处于可登记状态，进入真实场次测试阶段；管理端账号和部落列表已补充
> 本地即时搜索，最新小程序包仍需通过微信开发者工具上传后才能进入线上版本。

### 15.1 目标

在不改变第一版积分规则的前提下，补齐登记开关感知、新部落同步、场次安全操作和撤销后重开规则，
然后完成第一轮真实登记灰度。F8 完成前保持 `FARM_SYSTEM_REGISTRATION_ENABLED=false`。

### 15.2 P0 开发项

1. **登记能力状态**
   - API 返回 `registration_enabled`；
   - 前端关闭时禁用单个和一键登记，并显示明确说明；
   - 增加开关开、关两种接口和页面测试。
2. **新部落受控同步**
   - 管理页提交新 Tag 后进入同步队列；
   - 官方资料成功或存在可用 stale 缓存后才允许绑定；
   - 显示同步中、标签无效、官方失败和重试状态；
   - 不在普通读取请求中直接调用 COC API。
3. **场次安全操作**
   - 首次最终登记前允许在管理页修改开始搜战时间；
   - 创建、开放场次增加确认和参与部落数量提示；
   - 明确场次创建后新增、启用或转移部落只影响下一场。
4. **撤销后的重开规则**
   - 撤销后默认保持不可登记；
   - 由创建者显式重新开放指定匹配或部落；
   - 统一 `revoked` 在 `partially_registered` 和 `completed` 场次中的行为；
   - 增加积分、流水、场次状态和重复重开测试。

### 15.3 P0 生产操作项

这些项目不需要重新开发，但必须在打开登记开关前完成：

1. 指定唯一创建者账号，或形成等价的受控纠错方案；
2. 显式配置并记录第一轮时间误差窗口；
3. 选择一组真实内部匹配部落并创建场次；
4. 临时打开登记开关，验证内部匹配、外部匹配失败、可重试错误和重复登记；
5. 执行一次撤销和积分对账；
6. 确认无异常后再扩大白名单。

### 15.4 P1 运营能力

- 场次历史、比赛详情、积分流水、登记尝试和审计日志页面；
- 管理结果页展示胜负、积分前后值、登记人和时间；
- 账号页展示灰度资格，减少“账号已创建但不能登录”的误解；
- 登录、登记、时间不匹配、COC API 耗时和对账异常的聚合观测与告警；
- 停用账号、停用部落和转移部落的确认流程；
- 前端串行登记遇到令牌失效时停止剩余请求；
- 部落数量或真机耗时达到阈值后，再实现服务端可恢复批次任务。

### 15.5 F8 验收门槛

- 登记关闭时页面不会提供可点击的登记按钮；
- 管理员能够在页面中完成一个全新官方部落的验证与绑定；
- 场次时间修改、开放确认和快照提示符合业务语义；
- 撤销后不会未经创建者授权重新登记；
- 至少一组真实内部对手完成双方一致的结算；
- 至少一次外部对手保持积分不变；
- 重复登记不新增比赛或流水；
- 撤销后积分与流水对账通过；
- 互刷专项测试、相关接口测试和小程序生产构建通过；
- 完成生产备份、开关回滚和服务健康检查。

### 15.6 暂不纳入 F8

- 外部同盟部落和外部积分；
- 复杂轮转、权重、人工指定输赢、赛季和排行榜；
- 自动推断下一轮时间和全联盟后台自动登记；
- 多互刷联盟租户；
- 公开注册、短信验证和自行找回密码。
