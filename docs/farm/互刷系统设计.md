# 互刷联盟系统设计

> 状态：第一版核心能力和 F8 P0 代码已实现；生产仍处于只读灰度，登记关闭，待部署与真实场次验收
> 日期：2026-10-23
> 范围：独立账号登录、部落归属、统一场次、COC 对手登记、自动判定输赢和积分流水

## 1. 文档目的

本文定义小程序内“互刷联盟系统”的第一版业务规则、权限、页面、数据模型和接口边界，作为后续实现与验收依据。

本系统与现有“部落 → 互刷”统计页面是两个不同模块：

- 现有 `docs/14-farm-clans.md` 描述 `category=farm` 部落的配置、去速本、填坑号和不活跃成员统计；
- 本文描述独立账号密码登录的互刷联盟登记、匹配、输赢和积分系统；
- 新系统可以复用已有 COC 官方客户端和当前战争标准化能力，但不得复用微信登录权限，也不得改变现有 `farm-config` 接口语义；
- 新系统入口位于小程序“管理”页的“互刷联盟系统”卡片，源码已接入独立登录和系统首页；生产后端
  已对白名单账号开放。微信小程序线上包的具体发布版本需要在发布流程中单独核验，不能仅根据后端状态推断。

## 2. 第一版目标与非目标

### 2.1 第一版目标

1. 使用独立邮箱和密码登录互刷系统；
2. 一个账号代表一个“部落联盟组织”，每个账号可绑定一个或多个互刷部落；
3. 支持创建者、管理员、成员三种角色；
4. 全互刷联盟每轮使用统一时间，由创建者或管理员手工设置；
5. 登录账号可以逐个或一键登记自己名下的全部互刷部落；
6. 登记时由后端调用 COC 官方 API 获取当前部落战对手；
7. 对手属于本轮互刷部落时，系统按积分自动判定预定输赢并立即结算；
8. 对手不属于本轮互刷部落时，记为匹配失败，积分不变；
9. 所有成功结算通过积分流水记录，可审计、可撤销；
10. 重复登记、双方分别登记或并发登记不能造成重复随机、重复记录或重复积分。

### 2.2 第一版非目标

以下内容暂不开发，只保留扩展空间：

- 外部同盟部落与外部积分；
- 复杂匹配、轮转、权重或人工指定输赢算法；
- 赛季积分、排行榜和奖励；
- 根据实际星数或摧毁率重新判定互刷输赢；
- 自动创建账号、短信验证码、手机号和找回密码；
- 自动推断下一轮时间；
- 全联盟后台定时批量登记；
- 多个互刷联盟租户。

## 3. 业务术语

为避免“联盟”“账号”和“部落”混用，统一使用以下术语：

| 术语 | 含义 |
|---|---|
| 互刷联盟 | 整个互刷系统，第一版只有一个 |
| 部落联盟账号 | 独立邮箱密码登录的组织账号，代表一个部落联盟组织，不代表具体个人 |
| 互刷部落 | 实际参加互刷的 COC 部落，以标准化部落标签唯一标识 |
| 当前场次 | 当前唯一可登记的互刷轮次，包含统一时间和参与部落快照 |
| 登记 | 主动获取某个部落的当前战争对手并生成本场匹配结果 |
| 内部匹配 | 对手属于当前场次参与部落快照 |
| 匹配失败 | 对手不属于当前场次参与部落快照，积分不变 |
| 预定输赢 | 根据登记前积分计算出的互刷安排，不等同于 COC 实际战争星数结果 |

第一版的核心关系为：

```text
一个互刷联盟
  └── 多个部落联盟账号
        └── 每个账号绑定一个或多个互刷部落
```

## 4. 已确认的业务规则

### 4.1 账号与部落

- 每个部落联盟账号只有一个角色：`creator`、`admin` 或 `member`；
- 每个账号可以绑定一个或多个互刷部落；
- 一个互刷部落同时只能归属于一个账号；
- 部落转移到其他账号时，积分和历史记录继续跟随部落；
- 所有启用中的互刷部落默认参加下一场；
- 停用账号或部落不得删除历史事实；
- 第一版允许同一个账号在多台设备同时登录；
- 因账号代表组织并可能被多人共享，审计只能准确到账号，不能证明具体自然人身份。

### 4.2 场次与时间

- 同一时刻只允许存在一个当前场次；
- 全互刷联盟在一场中使用统一业务时间；
- 时间统一按北京时间输入和展示，数据库统一保存为 UTC；
- 创建者和管理员可以创建下一场并手工设置时间；
- 创建场次时，对所有启用部落建立参与快照，并保存其登记前积分；
- 任意部落成功登记后，场次时间锁定，管理员不能再修改；
- 创建者可以撤销整场后重新建立，但必须留下审计记录；
- 在场次建立后新增或重新启用的部落默认从下一场开始参加，避免中途改变内部匹配判断集合。

本文所称“统一开战时间”固定指全联盟“开始搜战的时间”，对应 COC 官方
`preparationStartTime`，不使用战斗日的 `startTime`。时间校验允许配置误差窗口，超出窗口的当前战争不属于本场。

### 4.3 登记与匹配

- 成员、管理员和创建者都可以登记自己账号下的部落；
- 用户可以点击单个部落的“登记本场”，也可以点击页面顶部“一键登记”；
- 一键登记只处理当前登录账号绑定的部落，不处理全联盟所有部落；
- 一键登记在后端串行或受控并发调用 COC API，避免突发请求；
- COC API 凭证只保存在后端环境变量中，绝不下发到小程序；
- 登记只使用官方 `GET /clans/{clanTag}/currentwar` 获取对手；
- 部落标签比较使用 COC 比较键：去空格、转大写、补齐 `#`，并将历史录入中可能出现的字母
  `O` 视为官方标签中的数字 `0`；数据库唯一约束不得把 `#YCOC` 与 `#YC0C` 当作两个部落；
- COC API 只用于确认本场战争和对手身份，不使用实际战争星数决定本文的预定输赢；
- 对手标签存在于当前场次参与部落快照时，视为内部匹配成功；
- 对手标签不在当前场次参与部落快照时，记为匹配失败，积分不变；
- 内部匹配由一条共享匹配记录表示；一方登记成功后，双方都显示相同结果；
- 后登记的一方直接复用现有结果，不再次请求、不再次随机、不再次结算。

### 4.4 第一版积分算法

- 每个部落初始积分为 `0`；
- 积分属于互刷部落，不属于登录账号；
- 积分允许为负数；
- 内部匹配比较双方的本场积分快照：
  - 积分较低的一方预定获胜；
  - 积分较高的一方预定失败；
  - 积分相同时随机决定一次；
- 预定胜方积分 `+1`；
- 预定负方积分 `-1`；
- 匹配失败双方不加分、不扣分；
- 平分时的随机结果必须永久保存，页面刷新或重复登记不得重新随机；
- 内部匹配成功后立即结算，不再要求管理员逐场确认；
- 创建者可以撤销错误结算，撤销通过反向积分流水完成，禁止直接删除原流水或覆盖历史。

示例：

| 登记前积分 | 系统判定 | 登记后积分 |
|---|---|---|
| A = -1，B = 2 | A 胜、B 负 | A = 0，B = 1 |
| A = 0，B = 0 | 随机一次，假设 A 胜 | A = 1，B = -1 |

## 5. 权限模型

### 5.1 权限矩阵

| 能力 | 成员 | 管理员 | 创建者 |
|---|---:|---:|---:|
| 独立账号登录、退出和修改自己密码 | 是 | 是 | 是 |
| 查看当前场次统一时间 | 是 | 是 | 是 |
| 查看自己账号绑定的部落 | 是 | 是 | 是 |
| 查看自己部落的积分和本场结果 | 是 | 是 | 是 |
| 登记自己账号下单个部落 | 是 | 是 | 是 |
| 一键登记自己账号下全部部落 | 是 | 是 | 是 |
| 查看全部账号和全部部落 | 否 | 是 | 是 |
| 设置每个账号包含哪些互刷部落 | 否 | 是 | 是 |
| 新增、停用和转移互刷部落 | 否 | 是 | 是 |
| 创建场次和设置统一时间 | 否 | 是 | 是 |
| 创建、停用部落联盟账号 | 否 | 仅成员账号 | 是 |
| 重置成员账号密码 | 否 | 否 | 是 |
| 设置管理员角色 | 否 | 否 | 是 |
| 初始化、停用或转移唯一创建者 | 否 | 否 | 受控运维入口 |

| 修改积分和核心规则 | 否 | 否 | 是 |

第一版不提供公开注册。管理员可以在管理页面创建和停用成员账号；创建者可以创建成员或管理员账号、
调整角色并重置密码。唯一创建者的初始化和转移仍使用受控运维入口。

唯一创建者不能在管理页面中停用或降级。需要转移创建者时使用受控运维流程完成，避免先降级旧创建者后无人有权提升新创建者。

### 5.2 数据范围

- 成员接口始终强制使用登录令牌中的 `farm_account_id` 过滤部落；
- 客户端提交其他账号 ID 或其他账号部落标签时，后端返回 404 或 403；
- 管理员和创建者通过独立的管理接口访问全局数据；
- 仅在前端隐藏按钮不构成授权，所有权限必须在后端再次校验；
- 微信 JWT 不能访问互刷系统接口，互刷 JWT 也不能访问微信用户私有接口。

## 6. 页面与交互设计

### 6.1 入口

入口继续放在小程序“管理”页、微信账号区域下方：

```text
互刷系统                              独立账号

互刷联盟系统
查看开始搜战时间、匹配结果与积分

[ 进入系统 → ]
```

未登录互刷系统时进入独立登录页；已存在有效互刷登录态时直接进入互刷首页。微信是否登录不影响互刷系统登录。

### 6.2 登录页

字段与行为：

- 登录邮箱；
- 密码；
- 登录按钮；
- 不提供微信一键登录；
- 不提供公开注册；
- 不提供短信找回密码；
- 提示“忘记密码请联系创建者”；
- 登录成功后将独立令牌保存到与微信令牌不同的存储键，例如 `farm_token`。

### 6.3 互刷首页

页面顶部：

- 管理员和创建者显示独立的“互刷联盟管理”入口，用于全联盟的账号、部落和场次设置；
- “互刷联盟管理”不与当前登录账号名称放在同一操作栏，避免被理解为“管理当前账号”；
- 当前登录账号的组织名称、角色、邮箱和“退出登录”单独显示；
- 本轮统一时间；
- 距离业务时间的倒计时或场次状态；
- 已登记数量，例如 `2/5`；
- “一键登记”按钮。

部落列表卡片：

```text
苍穹一部落                      当前积分 0
#ABC123
本轮状态：未登记

[ 登记本场 ]
```

内部匹配成功后：

```text
苍穹一部落  vs  对手部落
内部匹配成功 · 本场预定胜
积分：0 → 1

[ 已登记 ]
```

匹配失败后：

```text
匹配失败
对手：普通部落 #XYZ789
积分不变：0

[ 已登记 ]
```

每张部落卡片固定保留“对手部落”区域：未登记时显示“登记后显示”；登记后同时展示对手名称和标签。
内部匹配额外显示本部落的本轮胜负以及“赛前积分 → 当前积分”，不单独强调积分增减值；外部匹配失败也保留实际搜到的对手信息，
便于成员核对匹配结果。

### 6.4 管理页

管理员和创建者点击首页的“互刷联盟管理”后，先进入全联盟管理首页。该页不直接堆叠业务表单，
也不展示范围说明、功能选择标题或重复的功能介绍区，而是沿用普通联盟管理页的纵向卡片菜单：

```text
[场]  场次管理    ›
[部]  部落管理    ›
[号]  账号管理    ›
```

每张卡片使用同尺寸图标、标题和右侧箭头，可在卡片内保留一行简短说明；点击后进入对应的独立管理页：

- **场次管理**：当前场次、统一开始搜战时间、开放场次、全联盟登记进度和匹配结果；
- **部落管理**：互刷部落列表、新增、停用、启用和账号归属转移；列表支持按部落名称、标签以及所属
  账号名称或邮箱即时搜索；添加和转移部落时使用可按联盟名称或登录邮箱搜索的账号选择弹层；
- **账号管理**：独立账号列表、创建、角色、停用、启用和密码重置；列表支持按联盟名称、登录邮箱、
  角色或状态即时搜索；每个账号提供“编辑”入口，进入后
  查看该账号绑定的全部互刷部落、当前积分和启用状态，并可停用或重新启用部落。

后续的积分流水、审计和系统配置也按同样方式增加独立功能入口，不重新合并到一个长页面。

管理员和创建者的管理范围包括：

- 当前场次与统一时间设置；
- 账号列表和角色；
- 每个账号绑定的互刷部落；
- 新增、停用、转移部落；
- 全联盟登记进度与异常；
- 匹配结果和积分流水；
- 操作审计。

创建者额外可见：

- 设置账号角色；
- 撤销匹配结算；
- 撤销整场；
- 重置核心配置。

未实现的积分流水和审计页保持在后续阶段，不在当前管理首页展示无效占位入口。

## 7. 登记状态机

### 7.1 部落状态

| 状态 | 含义 | 成员能否重试 |
|---|---|---:|
| `not_registered` | 本轮尚未登记 | 是 |
| `registering` | 正在调用 COC API | 否 |
| `not_in_war` | 尚未搜到对手或官方返回 `notInWar` | 是 |
| `war_mismatch` | 当前战争不属于本轮时间窗口 | 是 |
| `fetch_failed` | API、权限、网络或数据校验失败 | 是 |
| `internal_matched` | 内部匹配成功并已结算 | 否 |
| `match_failed` | 对手不属于本轮互刷部落，积分不变 | 否 |
| `revoked` | 创建者已撤销原结果 | 仅创建者重新开放后可登记 |

`not_in_war`、`war_mismatch` 和 `fetch_failed` 不是匹配失败，不得混为同一状态，也不得改变积分。

### 7.2 场次状态

```text
scheduled → open → partially_registered → completed
                  ↘ cancelled
```

- `scheduled`：已创建，尚未到登记窗口；
- `open`：可以登记，但还没有最终结果；
- `partially_registered`：至少一个部落已有最终登记结果；
- `completed`：全部参与部落均为 `internal_matched` 或 `match_failed`；
- `cancelled`：创建者撤销整场，原匹配和积分流水保留为撤销状态。

## 8. 登记与结算流程

### 8.1 单个登记

```text
用户点击“登记本场”
  ↓
后端验证互刷令牌、当前场次和部落归属
  ↓
检查该部落是否已有最终结果
  ├── 有：直接返回已有结果
  └── 无：继续
  ↓
调用 CocApiClient.get_current_war(clan_tag)
  ↓
校验普通部落战状态、时间窗口、本方标签和对手标签
  ├── 暂无战争：not_in_war
  ├── 时间不符：war_mismatch
  ├── 调用失败：fetch_failed
  └── 有效战争：继续
  ↓
对手是否在当前场次参与快照中？
  ├── 否：match_failed，积分不变
  └── 是：锁定规范化部落对，进入数据库事务
             ↓
           检查双方是否已有匹配
             ├── 有：复用已有结果
             └── 无：比较积分快照，必要时随机一次
                        ↓
                      写入匹配、双方结果、两笔积分流水和审计日志
                        ↓
                      提交事务并返回结果
```

### 8.2 一键登记

- 一键登记获取当前账号本轮尚未最终登记的全部部落；
- 已经因对手登记而自动完成的部落直接跳过；
- 逐个调用与单个登记相同的业务服务，不复制算法；
- 默认串行执行，后续可按官方 API 限额调整为小并发；
- 页面持续显示进度，不因单个部落失败中止剩余部落；
- 返回每个部落的结果及汇总数量：内部匹配成功、匹配失败、暂未匹配、获取失败；
- 重复点击一键登记必须安全，不能重复结算。

### 8.3 时间校验

登记服务使用当前场次的业务时间与 COC 战争时间字段校验，防止把上一场或下一场战争登记到本场：

- 业务时间固定映射到 COC `preparationStartTime`；
- 误差窗口必须集中配置，不在代码中散落常量；
- 第一版由 `FARM_SYSTEM_TIME_TOLERANCE_SECONDS` 集中配置，默认 2700 秒并限制在 60–7200 秒；
- 超出窗口返回 `war_mismatch`，不保存最终匹配、不改变积分；
- 原始官方时间、标准化时间和校验原因必须保存在登记尝试记录中，便于排查。

## 9. 幂等、并发与一致性

以下约束属于第一版硬要求：

1. 同一部落在同一场次最多拥有一个最终结果；
2. 内部双方的规范化匹配键固定为 `min(clan_tag) + max(clan_tag)`；
3. 同一场次同一规范化匹配键只能有一条有效匹配记录；
4. 平分随机只在首次创建匹配时执行并保存；
5. 内部匹配的双方结果和两笔积分流水在同一个 SQLite 事务中写入；
6. 任一写入失败则整笔事务回滚；
7. 重复请求返回已有结果，不重复调用随机算法，不重复写积分；
8. A、B 同时登记时，数据库唯一约束和事务保证最终只存在一条匹配；
9. 撤销使用反向流水，不能修改或删除已生效的原流水；
10. 部落当前积分与积分流水必须能对账。

| `last_login_at` | 最近登录时间 |

数据库和服务层共同保证只有一个有效创建者账号。

| 字段 | 说明 |
|---|---|
| `id` | 主键 |

| `opponent_tag` / `opponent_name` | 对手快照 |

| `score_after` | 最终积分，可空 |

内部匹配或单边匹配失败记录。

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `round_id` | 所属场次 |
| `match_type` | `internal` / `failed_external` |

| `clan_a_id` / `clan_b_id` | 内部双方；失败时 `clan_b_id` 为空 |
| `opponent_tag` / `opponent_name` | 非内部对手快照 |
| `winner_clan_id` / `loser_clan_id` | 内部结果 |
| `score_a_before` / `score_b_before` | 判定依据 |
| `tie_break_used` | 是否使用随机决胜 |
| `tie_break_value` | 随机结果或可审计值 |
| `status` | `settled` / `revoked` |
| `settled_at` / `settled_by` | 结算信息 |
| `revoked_at` / `revoked_by` / `revoke_reason` | 撤销信息 |

### 10.6 `farm_score_ledger`

积分流水。

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `clan_id` | 积分所属部落 |
| `round_id` / `match_id` | 来源场次与匹配 |
| `entry_type` | `initial` / `win` / `loss` / `reversal` / `manual_adjustment` |
| `delta` | 第一版为 `+1`、`-1` 或撤销反向值 |
| `balance_before` / `balance_after` | 变更前后积分 |
| `reason` | 原因 |
| `created_by` / `created_at` | 操作账号和时间 |
| `reverses_entry_id` | 撤销时指向原流水 |

同一有效匹配、同一部落、同一基础结算类型必须唯一，防止重复积分。

### 10.7 `farm_registration_attempts`

保存每次用户触发登记的观测记录，包括请求账号、部落、场次、官方状态、官方时间、对手、错误类别和耗时。该表用于排障，不作为积分或最终结果事实。

### 10.8 `farm_audit_logs`

保存账号停用、角色变化、部落新增/转移/停用、场次时间变化、撤销结算等管理操作。日志记录结构化对象类型、对象 ID、修改前后摘要、操作账号和时间，不记录密码、令牌或完整外部授权信息。

只读一致性检查入口为 `scripts/audit_farm_system.py`。它使用 SQLite `mode=ro` 和
`PRAGMA query_only=ON`，检查物化积分与流水链、内部匹配的双方结果与基础流水、撤销反向流水及
已结束场次参与数量，只输出异常对象 ID，不自动修复生产数据。

## 11. API 设计建议

统一使用 `/api/farm-system` 前缀，避免与现有 `/api/clan/farm-config` 混淆。

### 11.1 登录与当前账号

```text
POST /api/farm-system/auth/login
POST /api/farm-system/auth/logout
POST /api/farm-system/auth/change-password
GET  /api/farm-system/me
```

登录响应签发独立受众的 JWT，例如 `aud=farm-system`，并携带 `farm_account_id`、`role` 和 `token_version`。互刷鉴权依赖只接受该受众。

### 11.2 成员首页与登记

```text
GET  /api/farm-system/dashboard
POST /api/farm-system/rounds/{round_id}/clans/{clan_tag}/register
POST /api/farm-system/rounds/{round_id}/register-all
GET  /api/farm-system/clans/{clan_tag}/score-ledger
```

- `dashboard` 只返回当前账号名下部落；
- 单个登记接口必须携带幂等键或使用数据库自然唯一键实现重复安全；
- `register-all` 只处理当前账号，可采用服务端受控串行，也可返回批次 ID；
- 首版如不引入后台任务，可由前端逐个调用单部落接口并显示进度，但单部落业务服务必须是唯一算法入口。

### 11.3 管理接口

```text
GET    /api/farm-system/admin/accounts
POST   /api/farm-system/admin/accounts
PATCH  /api/farm-system/admin/accounts/{account_id}
GET    /api/farm-system/admin/clans
POST   /api/farm-system/admin/clans
PATCH  /api/farm-system/admin/clans/{clan_tag}
POST   /api/farm-system/admin/clans/{clan_tag}/transfer
POST   /api/farm-system/admin/rounds
PATCH  /api/farm-system/admin/rounds/{round_id}
GET    /api/farm-system/admin/rounds/{round_id}/results
POST   /api/farm-system/creator/matches/{match_id}/revoke
POST   /api/farm-system/creator/rounds/{round_id}/cancel
```

所有接口在路由层校验角色，在服务层再次校验对象范围和状态转换。账号创建 UI 未完成前，可只保留受控脚本入口，但不得提供公开注册接口。

## 12. 认证与安全

- 第一版密码使用 Python 标准库 `hashlib.scrypt` 和随机盐，编码为可升级的 `scrypt-v1` 格式；禁止明文、可逆加密和日志输出；
- 登录邮箱去除首尾空格、转小写后唯一，并执行邮箱格式和长度校验；
- 登录接口限制失败次数和请求频率，错误信息不区分“账号不存在”和“密码错误”；
- 重置密码或停用账号时递增 `token_version`，使旧令牌失效；
- 互刷令牌使用独立存储键，退出微信账号不能误删互刷令牌，退出互刷系统也不能影响微信令牌；
- 管理接口禁止仅根据请求体中的角色授权；
- 部落标签统一去空格、转大写并补齐 `#`；
- COC API Token 继续只从环境变量读取，沿用官方域名白名单、HTTPS、超时和禁用环境代理策略；
- 对外错误不返回密码哈希、令牌、官方授权头、内部异常堆栈或其他账号私有数据。
- 灰度阶段可通过 `FARM_SYSTEM_ALLOWED_ACCOUNT_IDS` 限制独立账号范围；登录和每次鉴权都复核白名单。

数据库上线准备入口为 `scripts/prepare_farm_system.py`。默认只读预览，只有显式
`--apply --yes` 才写入；现有数据库会先通过 SQLite backup API 建立并验证一致性备份，迁移后再次
执行 `PRAGMA integrity_check` 并确认全部互刷表存在。脚本可重复执行，不删除或清空业务事实。

## 14. 异常与边界处理

| 场景 | 第一版行为 |
|---|---|
| COC 返回 `notInWar` | 记 `not_in_war`，允许重试，积分不变 |
| 战争日志不可访问或 API 403 | 记 `fetch_failed`，允许重试，积分不变 |
| 网络超时或官方 API 失败 | 记 `fetch_failed`，其他部落继续登记 |
| 当前战争时间不属于本轮 | 记 `war_mismatch`，允许重试，积分不变 |
| 当前战争是 CWL | 视为不符合互刷登记，返回明确错误，积分不变 |
| 对手标签缺失或格式非法 | 记 `fetch_failed`，不猜测对手 |
| 对手不是本轮参与部落 | 记 `match_failed`，积分不变 |
| 双方同时登记 | 唯一约束保证只结算一次，另一请求读取已有结果 |
| 同账号一键登记中某部落失败 | 继续处理其他部落并汇总结果 |
| 部落在场次中途转移账号 | 当前场次按快照归属展示，下一场使用新归属 |
| 创建者撤销匹配 | 写反向积分流水，双方状态改为 `revoked`，保留原记录 |
| 当前场次已存在 | 禁止再创建第二个未结束场次 |

### 18.2 F8 P0 开发完成情况

1. **登记能力状态已实现**：`dashboard.registration_enabled` 下发实际开关状态；关闭时单个登记和
   一键登记均禁用，并显示“登记功能暂未开放”。后端写接口仍保留独立开关校验。
2. **新部落官方资料同步闭环已实现**：管理页先创建 `clan_profile` 互动同步任务并轮询状态；官方资料
   成功或存在可用 stale 缓存后才允许绑定，失败可重试。普通读取和绑定请求均不直连 COC API。
3. **场次安全操作已实现**：首次最终登记前可修改开始搜战时间；创建和开放均有二次确认；页面显示
   参与部落数量，并明确说明创建后新增、启用或转移的部落只参加下一场。
4. **撤销后重开规则已实现**：`revoked` 默认不可再次登记；只有创建者可显式“重新开放”，原匹配、
   原积分流水和反向流水继续保留，双方回到未登记状态。重复重开和重新结算均有回归测试。

以上为当前工作分支实现状态，尚不能等同于生产已部署；部署前继续保持登记开关关闭。

### 18.3 正式开放登记前必须完成的生产操作

以下不是新功能开发，但属于生产登记的前置条件：

1. 部署 F8 后端和小程序包，但保持 `FARM_SYSTEM_REGISTRATION_ENABLED=false`；
2. 显式设置并记录时间误差窗口，第一轮可继续采用 2700 秒；
3. 选择一组真实内部对手，临时打开登记开关，验证双方结果、积分流水、重复登记和并发幂等；
4. 验证一次外部对手匹配失败、一次可重试错误和一次创建者撤销后重开；
5. 对账通过后再逐步扩大白名单，不能直接全量开放。

### 18.4 第二优先级运营能力

- 场次历史列表，以及比赛、积分流水、登记尝试和审计日志详情页；
- 管理结果页补充双方胜负、登记前后积分、登记人和登记时间；
- 在账号管理页展示灰度资格，避免账号创建成功但因不在白名单而无法登录；
- 登录失败、登记失败、时间不匹配、COC API 耗时和积分对账异常的聚合观测与告警；
- 停用账号、停用部落和转移部落增加确认步骤；
- 账号部落数量增多或真机串行体验不可接受时，把一键登记升级为可恢复的服务端批次任务；
- 前端串行批次遇到令牌失效时应停止剩余请求，并保留可继续登记的范围。

### 18.5 后续业务版本，不纳入首次正式开放

- 外部同盟部落和外部积分；
- 复杂轮转、权重或人工指定输赢算法；
- 赛季、排行榜和奖励；
- 自动推断下一轮时间和后台自动批量登记；
- 多个独立互刷联盟租户；
- 公开注册、短信验证和自行找回密码。
