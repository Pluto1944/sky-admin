## 1. 文档定位

本文档统一收录 `sky-admin` 从苍穹联盟内部工具扩展为多用户、多联盟平台时，除账号体系外的系统模块问题。

当前阶段已经落地多联盟技术底座，但不提前确定套餐价格和对外 SLA。认证冲突由作者人工处理；
自助验证码和正常移交本轮均暂缓，平台先通过人工后台处理。所有未逐项讨论的数字和运营建议仍需
在真正开放对应批次前复核。

联盟、用户、角色、加入、分享、部落认证和前端联盟切换见 [账号体系设计](./账号体系设计.md)。系统不再引入“个人空间”或独立于联盟之外的租户模型。

## 2. 总体目标

- 使用统一的联盟实体承载免费和付费用户；
- 每个用户可以创建一个免费联盟，默认名称为“我的部落”，可自定义名称并订阅最多 3 个部落；
- 普通会员和高级会员最多添加 10 个部落；高级会员获得后台高频自动同步；
- 部落认证按 `alliance_id + clan_tag` 单独进行，套餐和认证分别控制同步权益与管理数据权限；
- 相同部落的公共数据只采集和存储一份；
- 用户请求只读取缓存或业务库，不直接触发 COC 官方 API；
- 高并发或上游故障时可限流、降级和使用旧缓存；
- 联盟私有名单、标签、备注和管理统计严格隔离；
- 现有苍穹联盟在迁移过程中不因新架构而功能回退。

## 3. 总体数据流

```text
免费联盟 / 付费联盟 / 活跃战争
                    ↓
              同步需求汇总
                    ↓
        按部落和资源全局去重
                    ↓
         计算同步等级与下次执行时间
                    ↓
           任务队列 / Worker
                    ↓
          COC API 及其他授权数据源
                    ↓
         公共事实库 / 联盟私有业务库
                    ↓
              API 读取与鉴权层
                    ↓
              小程序当前联盟
```

同步调度与前端请求必须解耦。页面访问量增长不应等比放大对 COC API 的请求量。

### 3.1 当前容量基线（只读检查快照）

本设计基于当前约 12 个自有部落、8 个互刷部落、445 名在部成员和 12 支联赛队伍的只读检查结果。检查时服务器 CPU、内存和数据库体积均较轻，主要瓶颈是外部 API 串行请求以及单进程调度器的队头阻塞，而不是机器算力。

- 当时 `cwl_live` 一轮约 87.5 秒，在准备场次仍高频轮询的状态下估算约 3.2 万～4.1 万次外部请求/天；准备日频率已经由后续独立改动优化，但实时任务与长任务共用串行循环的问题仍然存在；
- `player_details` 对约 445 名成员逐个请求，一轮约 639 秒；
- 月底竞赛统计也可能形成约十分钟的串行阻塞窗口；
- 当前约 76 MiB 主数据库中，大部分空间来自 CWL 和普通战完整原始 JSON，结构化成员战争事实只占较小部分；
- 正常小程序页面读取 SQLite 缓存，不会因用户浏览量直接等比例增加 COC 请求。

上述数字是特定时间点的估算，不是容量承诺。未来必须用统一请求计数器、队列延迟和数据新鲜度指标替代人工估算。当前苍穹付费部落的具体刷新优化由独立工作处理，本设计不重复修改其现行频率。

## 4. 免费单部落标签与现有功能

### 4.1 标签定位

普通用户创建免费联盟并订阅唯一一个部落时，需要为该部落选择主要业务标签。标签不是装饰字段，而是现有页面、统计任务和默认展示列的功能选择器。

“我的部落”只表示免费联盟创建时的默认名称，不是独立的个人模式或单独系统模块。免费联盟与付费联盟
共用联盟、成员、部落管理和认证模型；前端统一从“管理联盟 / 管理部落”进入，套餐差异只体现在数量、
刷新质量和功能权益。

第一版免费联盟提供以下四个选项：

| 内部值 | 用户侧名称 | 定位 |
| --- | --- | --- |
| `normal` | 实战 | 以普通部落战和 CWL 为主要用途 |
| `combat` | 战营 | 作为联盟的普通战历史攻防统计对象 |
| `farm` | 互刷 | 以互刷配置、去速本和清退辅助为主要用途 |
| `flat` | 偷矿 | 以都城突袭和成员贡献为主要用途 |

`alliance_clans.category=combat` 表示联盟日常页面中的“战营”，用于选择普通战统计对象；它不再承担
“本月参加 CWL 的队伍”语义。CWL 参赛队伍按月份单独配置，月度队伍中的 `combat / shell`
只是当月联赛编排类别，不改变日常部落标签，也不要求该部落已经订阅或认证。

标签保存在联盟与部落的订阅关系中，即 `alliance_id + clan_tag + category`。标签不代表部落已经认证，不改变用户角色，也不能提高免费套餐的同步等级。

### 4.2 当前小程序能力基线

标签展示必须以当前已经存在的页面和数据为基础：

| 当前模块 | 当前实际能力 | 多联盟改造前的限制 |
| --- | --- | --- |
| 部落概览 | 展示平均大本、人均奖杯、赛季捐兵、首领、部落战状态和都城状态 | 当前从静态 `config/settings.yaml` 读取自有部落 |
| 单部落详情 | 展示官方资料、部落战胜平负、联赛等级、奖杯、都城、标签、大本和职位分布、捐兵 | 当前只允许配置中的自有部落 |
| 成员 | 已有基础资料、赛季进攻、捐收兵、普通战、CWL、一星、漏刀、都城、竞赛和最近活动列 | 当前是整个苍穹联盟的跨部落大表 |
| 战营 | 已有普通战前 5/15/45 场和联赛前 1/3/6 月攻防统计 | 普通战按当前联盟 `category=combat` 查询；联赛统计按当前联盟月度联赛队伍配置查询 |
| 互刷 | 已有实时大本配置、去速本配置、去速本候选、填坑号和最不活跃成员 | 只读取 `category=farm`；填坑号来自苍穹本地名单，外部部落没有现成来源 |
| 部落战 | 已有当前战争、单场详情和最近 15 场历史 | 当前覆盖所有四种现有类别，数据来自本地缓存 |
| 联赛数据 | 已有参赛部落、战斗日和四项总览表 | 已改为联盟按月配置队伍、公共 CWL 事实全局复用，并已完成生产迁移 |
| 联赛点名 | 已有集结检查、当前未出刀和历史漏刀 | 已按当前联盟月度联赛队伍过滤；战争事实按 Tag 复用，集结数据仍依赖已有正式名单快照 |

因此不能因为选择某个标签就假设系统已经存在对应新页面。例如当前没有独立“偷矿”页面；第一版只能复用概览、成员表和已有都城数据。

### 4.3 标签对应的页面入口

| 页面或入口 | 实战 | 战营 | 互刷 | 偷矿 |
| --- | :---: | :---: | :---: | :---: |
| 部落概览和单部落详情 | 显示 | 显示 | 显示 | 显示 |
| 基础成员名单 | 显示 | 显示 | 显示 | 显示 |
| 战营统计 | 无战营提示 | 显示 | 无战营提示 | 无战营提示 |
| 互刷统计 | 无互刷部落提示 | 无互刷部落提示 | 显示 | 无互刷部落提示 |
| 当前部落战 | 显示 | 显示 | 显示 | 显示 |
| 最近部落战 | 可查看 | 可查看 | 可查看 | 可查看 |
| 联赛数据 | 月度队伍已配置则显示，否则提示无数据 | 同左 | 同左 | 同左 |
| 联赛点名 | 月度队伍已配置且缓存存在则显示，否则显示空状态 | 同左 | 同左 | 同左 |

标签不能隐藏已经真实发生的普通战争；标签只决定默认入口、专项统计和默认列。CWL 不从日常标签
自动推断，而由联盟管理员按月显式配置参赛队伍。联赛数据、单队详情和战营联赛统计
均读取当前联盟月度配置；无配置时显示“当前联盟本月暂无联赛队伍”。联赛报名仍是苍穹
专属能力；联赛点名入口及读取接口已经联盟化，不再按联盟名称拦截。

“实战统计”第一版复用现有 `ClanStats` 交互，已按当前联盟订阅关系中的 `category=combat`
选择战营部落；苍穹和其他联盟使用相同接口与规则，不按联盟名称或固定 `#2QQ` 分支。
接口已预留 `combat_clans`，后续一个联盟存在多个战营时可增加前端切换。现有“联赛点名”属于
联盟运营流程，按当前联盟月度联赛队伍读取：出刀提醒复用 `period + clan_tag` 的公共战争缓存，
集结检查复用同 Tag 的名单核对缓存；该能力不由日常部落标签直接决定。

### 4.4 概览与成员列

概览卡片优先展示当前已经能取得的数据：

| 标签 | 默认重点字段 |
| --- | --- |
| 实战 | 平均大本、人均奖杯、赛季捐兵、首领、部落战状态 |
| 战营 | 平均大本、成员数、普通战窗口统计、部落战状态 |
| 互刷 | 平均大本、成员数、赛季捐兵、首领、部落战状态 |
| 偷矿 | 平均大本、成员数、都城奖杯、都城联赛、都城状态 |

成员页继续复用现有字段，但按标签设置默认列，而不是为每个标签建立新的成员数据模型：

| 标签 | 默认成员列 |
| --- | --- |
| 实战 | 昵称、职位、大本、联赛段位、赛季进攻、捐收兵、部落战近 15 场、联赛近 3 月、一星率、漏刀率、最近活动 |
| 战营 | 昵称、职位、大本、普通战近 5/15/45 场攻防数据、最近活动 |
| 互刷 | 昵称、职位、大本、捐收兵、竞赛贡献、最近活动；专项页面另显去速本、填坑和不活跃名单 |
| 偷矿 | 昵称、职位、大本、都城近 4 周、都城出刀、平均每刀掠夺、竞赛贡献、最近活动 |

列的可见性仍需叠加账号体系中的成员与管理权限。标签只回答“这类部落默认关注什么”，不能让普通成员看到历史漏刀、不活跃判断或其他管理数据。

### 4.5 互刷与偷矿的现实边界

- 互刷的实时大本配置、去速本配置和候选名单可以复用现有 `farm_stats` 逻辑；
- 外部免费部落没有苍穹现有的填坑号数据源，未建立用户录入或导入机制前应隐藏填坑号区域，不能把空结果解释为“没有填坑号”；
- 最不活跃成员可以复用现有活动观察数据，但只对已认证部落的管理员和首领开放；
- 偷矿目前复用部落详情中的都城奖杯、都城联赛和状态，以及成员表中的都城近 4 周统计；
- 当前不存在独立偷矿页面，是否新增必须在后续页面设计中单独确认。

### 4.6 标签管理与首版边界（基础已实现）

`normal / combat / farm / flat / other` 标签、别名、排序及审计已实现。下列 30 天冷却、
外部互刷填坑号导入和独立偷矿页仍是未实现草稿：

- 联盟首领可添加或移除部落；首领和管理员都可修改别名、标签和顺序，不以部落是否已认证作为编辑前提；
- **未实现草稿：**标签修改设置 30 天冷却，避免通过反复切换触发不同专项任务；实施前需确认是否真有必要；
- 修改标签只改变页面入口、默认列和未来专项任务，不删除已经保存的公共历史或成员事实；
- “其他”作为长期兜底类型保留，不能强迫所有部落选择并不符合实际的玩法；
- 免费 CWL 不依赖苍穹腾讯文档报名，但仍需联盟管理员配置当月参赛部落；系统再从这些 Tag
  发现官方联赛组和 `war_tag`，不能扫描或猜测任意部落；
- 外部互刷部落第一版不开放填坑号导入，相关区域隐藏；以后如开放，仅允许已认证管理员手工维护或导入联盟私有名单；
- 第一版不新增独立偷矿页面，复用概览、成员和现有都城字段；实际使用反馈明确后再决定是否拆页。

### 4.7 月度联赛队伍通用化（已讨论确认，本地已实现）

每个联盟按月份维护自己的 CWL 队伍清单。配置是联盟私有运营数据，官方分组、战争和成员战绩
仍是按 `period + clan_tag`、`war_tag` 保存的全局公共事实。同一个 CWL 部落被多个联盟配置时，
只同步一次官方数据，各联盟通过自己的月度配置读取同一份缓存。

月度配置与日常 `alliance_clans` 订阅完全独立：

- 联赛部落不要求已经加入联盟的日常部落列表，也不要求完成部落认证；
- `combat / shell` 只描述该月队伍在联赛编排中的类别，不改变日常页面标签；
- 免费联盟每月最多配置 3 支联赛队伍；普通会员和高级会员每月最多配置 10 支；内部版当前上限 100 支；
- 上限由套餐权益 `max_cwl_teams` 提供，不在接口或前端写死；日常订阅部落上限仍按现有
  免费 1 个、付费 10 个计算，两种额度不能混用。

配置生命周期为：

1. `draft`：可新增、删除、修改、排序；
2. `active`：管理员确认后开始同步，在尚未发现官方联赛组前仍允许修改；
3. `frozen`：发现任一配置队伍的官方联赛组后冻结普通编辑；
4. `complete`：该月全部已发现队伍完成最终归档后进入只读历史。

冻结后如 Tag 配错，只能通过带操作者、原因和前后值的“纠正 Tag”审计操作处理，不能静默修改
既有分组、战争或成绩关联。管理员可配置当前月和下月，历史月份只读；离线迁移和补档工具可按
明确参数写历史月份。2026-06 的同月双联赛继续只保留月初赛季，月中赛季不进入月度统计。

苍穹第一版不要求管理员重复录入：现有月度编排完成后，把 `league_teams` 的结果幂等同步到
联盟月度配置表；历史结构化数据也从 `league_teams` 完整迁移。原有腾讯文档报名、编排、公示和
排名流程保持不变。其他联盟第一版只支持联赛数据和月度队伍配置，不开放联赛报名。

能力开关明确拆分：所有已支持联盟均可有 `cwl_data=true`；苍穹额外为
`cwl_registration=true`、`registration_source=tencent_docs`，其他联盟为
`cwl_registration=false`。联赛数据接口不得依赖报名能力，非苍穹前端也不显示报名入口或
“后续开发”等占位文案。

首版设置入口位于“管理 → 管理联盟 → 管理联赛部落”（子页标题为“联赛设置”），支持选择月份、复制上月、
创建下月联赛、增删改队伍、设置 `combat / shell`、调整顺序和确认。管理页完整列出所选月份队伍，
每行可编辑部落 Tag、显示名称和队伍别名。无配置时提供显式创建月份入口；已配置但尚未取得
官方数据时显示“本月已配置 N 支联赛队伍，等待官方联赛数据”。联赛数据页和单队详情使用当前
联盟月度配置。联赛点名同样读取当前联盟月度配置并复用按 Tag 保存的缓存；联赛报名继续由
`cwl_registration` 能力单独控制。

## 5. 套餐与权益模块

### 5.1 责任

- 定义免费版、普通会员、高级会员和内部套餐；内部版新库默认 100 个部落，但保留数据库中的运营配额与自定义权益；
- 免费版最多 3 个部落，普通会员和高级会员最多 10 个部落；
- 免费版和普通会员使用按需刷新与低频保底，高级会员使用后台高频自动刷新；
- 免费联盟和付费联盟共用联盟、成员、角色、分享和认证模型，升级只更换套餐权益；
- 记录每个联盟的有效套餐、配额、有效期和功能开关；
- 向同步模块输出质量等级，而不是让套餐模块自己执行同步；
- 向 API 层输出功能权益，角色和部落认证仍由账号体系分别判断；
- 免费联盟升级后保留原 `alliance_id`、成员关系、分享关系、认证记录和历史数据。

### 5.2 已确定的历史权益

免费联盟与付费联盟暂时采用相同的历史保存范围和页面统计窗口。普通战、CWL、都城、竞赛及成员统计不因免费套餐而主动缩短历史；现有 5/15/45 场、近 1/3/6 月等统计能力在数据来源通用化后可以保持一致。

免费与付费的主要差异放在可订阅部落数量、自动刷新频率、同步可靠性和管理功能，不通过缩短免费用户的历史数据制造差异。相同部落的公共事实全局只保存一份，多个联盟订阅时复用同一份战争、成员和统计事实；套餐控制访问和刷新质量，不复制公共历史。

### 5.3 套餐模型

**已讨论确认（2026-10-18）：**免费套餐固定 3 个部落；普通会员和高级会员均最多 10 个部落，不按数量区分两档，主要以是否提供后台高频自动刷新区分。

以下套餐行为中，付费到期规则已经讨论确认，其余仍为**建议草案（未逐项讨论）**：

- 成员数不作为核心计费维度，COC 单部落成员上限固定，按成员计费会增加理解和核算成本；
- 高级套餐可以增加刷新质量、联赛持续跟踪、管理统计、失败提醒和跨部落能力，但免费与付费历史范围暂时一致；
- 已认证免费联盟的管理员和首领可以使用已经采集到的管理数据，区别是数据更新较慢且不承诺付费可靠性；
- 同一部落被多个联盟订阅时只执行一次最高质量采集，内部记录需求来源；具体成本归属用于运营分析，不复制请求向每个联盟计费；
- **已讨论确认：**普通会员和高级会员到期后提供 7 天只读宽限期，停止日常部落和联赛配置写入，保留原部落、原同步等级、读取和续费入口；
- **已讨论确认：**宽限期结束自动降为免费套餐，只保留排序最前且不超过 3 个的部落继续低频同步，其余订阅转为非活跃；不删除公共历史、联盟成员、认证和审计记录；
- 两档会员的价格、有效期、支付续费方式、SLA 和退款规则留到正式收费前确定。

## 6. 同步控制模块

### 6.1 责任

- 接收各联盟套餐、订阅部落和战争状态产生的同步需求；
- 将多个联盟对同一部落的公共数据需求合并为一个实际同步目标；
- 按所有有效需求中的最高质量等级执行一次公共采集；
- 根据无战争、准备日、战斗日、CWL 活跃期等状态动态计算频率；
- 统一处理任务去重、优先级、限速、重试、超时和死信；
- 上游失败时保留旧数据并记录数据新鲜度；
- 套餐降级或订阅取消后，重新计算该部落的有效同步等级。

部落是否已认证不直接决定公共数据的同步频率；同步质量主要由有效套餐和战争状态决定。认证只决定联盟管理数据权限，避免把身份认证与资源调度耦合。

### 6.2 免费部落战争刷新方案（已讨论确认）

免费部落采用“手动实时刷新 + 最低限度自动保底”，不照搬当前苍穹部落战和 CWL 的高频自动刷新。

自动任务只承担战争生命周期完整性：

1. 每 6 小时低频探测普通战争状态；
2. 检测到准备日后保存 `start_time` 和 `end_time`，在开战附近自动确认一次；
3. 战争结束后自动拉取最终结果并归档，保证历史、出刀、漏刀和成员统计有完整事实；
4. 最终归档失败时按 10、30、60 分钟退避重试；
5. CWL 月初自动发现联赛组并保存各场 `war_tag`、开始和结束时间；
6. CWL 每场结束后同样执行一次自动最终确认和归档。

战争进行过程中的中间进度主要由正在合法浏览页面的访问者进入页面、显式点击“刷新战况”或在列表顶部
继续下拉触发。页面进入只检查一次，不会因用户停留而按冷却间隔持续请求。访问者不必加入
联盟；有效成员、已有浏览历史的登录用户和持有效分享令牌的未登录访客，均遵循同一个页面访问上下文。
手动刷新必须：

- 先返回当前缓存，不能让页面请求同步阻塞调用 COC API；
- 只向后台任务队列提交一个刷新请求；
- 按 `clan_tag + resource_type` 全局去重，同一部落多个用户的请求合并；
- 使用部落级共享冷却时间，不按用户分别产生请求；
- 展示“已提交刷新、刷新完成、刷新失败和当前缓存时间”等真实状态；
- 只允许刷新当前页面上下文中的联盟和部落，失效分享令牌或任意 Tag 请求必须拒绝；
- 刷新不提升成员、管理或字段可见权限。

已实现的共享冷却时间与付费自动刷新间隔使用同一策略：

| 当前状态 | 手动刷新最短间隔 |
| --- | --- |
| 无战争、已结束 | 5 分钟 |
| 准备日 | 30 分钟 |
| 距开战不足 30 分钟 | 2 分钟 |
| 战斗日 | 2 分钟 |

免费版只把实时中间进度交给手动刷新，低频状态探测、开战确认和结束归档仍是自动任务。完全依赖手动操作会使战争历史和成员评价取决于用户是否记得刷新，因此不采用纯手动模式。

高级会员继续使用后台自动高频刷新；免费版和普通会员即使因其他高级会员联盟订阅同一部落而复用了更新鲜的公共缓存，也不会因此获得高级会员的刷新可靠性或其他套餐权益。各套餐暂时采用相同历史保存范围。

完整页面映射、统一接口、CWL 冷却和前端状态见
[`免费联盟页面手动刷新设计.md`](免费联盟页面手动刷新设计.md)。上述间隔后续仍需根据 COC API 预算、
部落数量和灰度监控结果调整，但必须保持公共资源级去重，不能退回到按用户分别调用外部 API。

### 6.3 免费部落成员数据刷新结论（已讨论确认）

免费部落不执行每日全成员详情扫描。当前实现已经可以从部落资料中的成员列表取得大部分成员基础字段，包括昵称、玩家标签、职位、大本等级、奖杯、联赛、赛季进攻、捐兵和收兵；普通部落战、CWL、都城突袭则分别由对应的战争事实、联赛事实和都城突袭数据提供。因此，这些页面和统计不应为了补齐成员资料而逐个调用 `/players/{player_tag}`。

免费部落的成员数据按以下来源和策略处理：

| 数据或功能 | 主要来源 | 免费版刷新策略 |
| --- | --- | --- |
| 成员身份、职位、大本、奖杯、联赛、赛季进攻、捐收兵 | 部落资料的成员列表 | 随免费部落的低频基础同步更新，不逐成员请求 |
| 普通战与 CWL 进攻、三星、一星和漏刀 | 普通战与 CWL 最终归档事实 | 按战争生命周期探测和最终归档规则更新 |
| 都城贡献与出刀 | 都城突袭数据 | 按都城业务统计窗口采集，不依赖玩家详情 |
| 竞赛贡献 | 玩家详情中的 `Games Champion` 成就 | 只在竞赛月结统计窗口逐成员读取，每月一次即可 |
| 最近活动估算 | 成员列表字段变化，加上普通战和 CWL 出刀事实 | 随基础同步和战争归档更新；允许按需刷新套餐精度低于高级会员 |
| 账号绑定、身份校验和异常补数 | 单个玩家详情 | 由用户事件或修复任务按需读取，不做整部落周期扫描 |
| 英雄、兵种、宠物、装备和玩家家园 | 玩家详情 | 当前免费版没有对应功能，不纳入常规采集 |

最近活动时间不要求依赖玩家详情才能工作。成员列表中的捐收兵、经验、大本和赛季进攻等变化，以及普通战和 CWL 出刀，都可以作为活动证据。玩家家园变化只能提供一个额外且较弱的信号，不足以成为免费版每日扫描约 50 个玩家的理由。新赛季字段重置仍需按现有活动判定规则处理，不能把系统性重置误判为玩家主动活动。

由此，免费部落日常成员同步的主要成本是一次部落资料或成员列表请求，而不是成员人数规模的逐玩家请求。逐玩家详情采集只保留在以下边界：

1. 竞赛结束后的月度贡献结算；
2. 用户绑定、部落认证等单次业务操作；
3. 单个玩家数据缺失或异常时的定向修复；
4. 将来明确上线英雄、兵种、装备或玩家详细档案功能后，再按独立缓存和配额方案启用。

当前付费部落已有的 `player_details` 刷新频率和任务去留不在本次免费版设计中调整，由付费同步方案另行审查。本节只确定未来免费部落不得直接照搬现有全成员详情任务。

### 6.4 免费部落首次订阅初始化（核心已实现）

> 订阅后异步提交部落资料、成员列表和当前战争，公共缓存复用、全局去重、共享冷却和前端状态轮询已实现。
> “后台补全”中的完整历史回填、都城与其他低频资源仍是未来草稿，不是首次订阅的已上线保证。

免费用户首次订阅部落时，不等待夜间低频任务，但页面请求也不得直接串行调用一组外部 API。订阅成功后由同步控制模块生成一次可去重的初始化计划，并按资源优先级异步执行。

#### 立即初始化

以下数据关系到用户能否确认订阅对象和查看当前状态，应进入高优先级队列：

1. 校验部落 Tag 是否存在，并保存部落名称、等级、成员数、标签等基础资料；
2. 获取当前成员列表，建立成员基础快照；
3. 检测当前普通战或 CWL 状态；
4. 如果已经存在满足新鲜度要求的公共缓存，直接复用缓存，不再次调用外部 API；
5. 如果缓存过期，只为过期的资源创建任务，不重建整套初始化任务。

订阅接口只负责保存订阅关系并返回初始化状态，不能等所有采集完成后才响应。首屏可以立即显示已有缓存；没有缓存时显示“正在初始化”，不能把尚未同步解释为“没有数据”。

#### 后台补全

以下数据进入普通或低优先级后台队列，不阻塞首次进入页面：

- 在已有授权数据源和请求预算允许时，补充最近普通战历史；
- 检测到 CWL 后发现当前联赛组，并补充可取得的当月对局；
- 补充最近一期可取得的都城突袭数据；
- 对已有公共战争、联赛和都城历史执行结构化统计投影；
- 历史来源不可用或回填尚未完成时，明确显示可用时间范围，不能把部分历史标记为完整历史。

免费与付费采用相同历史保存范围，是指已经取得的数据使用相同保留规则，并不保证一个从未被系统采集过的新部落能够在首次订阅时立即补齐全部历史。

#### 不在首次订阅触发的任务

- 不逐个请求约 50 名成员的玩家详情；
- 不因首次订阅提前执行整部落竞赛结算，竞赛贡献等待统一的月结窗口；
- 不启动持续高频的普通战或 CWL 轮询；
- 不执行依赖苍穹腾讯文档、正式名单或内部配置的联盟运营流程。

#### 失败、重试与防滥用

- 每项资源分别记录 `pending / running / ready / partial / failed` 状态、数据时间和失败原因；
- 单项失败不撤销订阅，也不能覆盖其他已经成功的数据；
- 失败任务按统一退避策略重试，页面展示缓存时间和重试状态；
- 初始化任务按 `clan_tag + resource_type` 全局去重，同一部落被多个联盟订阅时只执行一次实际采集；
- 删除后重新添加同一部落，或多个用户同时添加同一部落，不能绕过资源冷却时间；
- 免费联盟更换订阅部落的具体冷却期限留待套餐规则确定，但底层任务去重和限频必须从第一版实施。

### 6.5 免费部落完整刷新时间表（建议草案，未逐项讨论）

免费部落的周期任务统一使用北京时间（`Asia/Shanghai`）。夜间任务不在某一分钟同时启动，而是按 `clan_tag` 稳定散列到指定窗口，确保同一部落每天的执行时间相对稳定，同时避免部落数量增长后形成瞬时请求洪峰。

| 数据或任务 | 免费版周期 | 实施规则 |
| --- | --- | --- |
| 部落资料与成员名单 | 每天一次，分散到 02:00～06:00 | 一次基础同步更新部落资料、成员快照和可由成员列表取得的字段；同一部落全局去重 |
| 普通战状态 | 每 6～12 小时保底探测 | 准备日记录时间点、战斗日允许受限手动刷新、结束后自动归档；具体冷却沿用 6.2 |
| CWL 状态与对局 | 月初低频发现，并按已知时间点确认 | 进行中的中间进度主要依靠受限手动刷新；每场结束后自动最终确认和归档，不进入付费两分钟轮询 |
| 互刷去速本统计 | 每日基础同步后重新计算 | 复用成员快照与当前战争缓存，不建立独立外部 API 拉取任务 |
| 都城成员统计 | 每周二凌晨一次 | 在凌晨窗口内按部落错峰执行，读取都城突袭事实，不逐玩家读取详情 |
| 竞赛贡献 | 每月 29 日凌晨开始 | 全部免费部落按队列错峰，可跨数小时完成；逐成员详情只服务本次月结，不与首次订阅或每日任务绑定 |
| 最近活动估算 | 事件驱动派生 | 成员基础同步、普通战归档和 CWL 归档成功后增量更新，不单独调用外部 API |
| 玩家详情 | 无全量周期任务 | 仅用于竞赛月结、账号绑定、认证校验和异常补数 |
| 历史统计投影 | 对应事实写入后执行 | 只读本地事实并增量计算，不占用外部 API 配额 |

周期执行还必须遵守以下规则：

1. 调度器停机或错过窗口后可以补跑，但补跑任务仍需经过全局去重、优先级和限速；
2. 免费离线任务不能挤占付费联盟正在进行的普通战和 CWL；
3. 上一轮尚未完成时不得为同一部落和资源重复排队；
4. 外部接口失败时保留上次有效数据，并显示缓存时间和失败状态；
5. 部落标签决定页面和默认统计重点，不得导致相同基础资料被重复采集；
6. 当前苍穹付费部落的现有刷新频率和任务拆分不在本表中调整。

### 6.6 同步质量等级（核心已实现，参数待调优）

同步质量描述“系统应以多快、多可靠的方式取得数据”，不等同于用户角色、部落认证或页面权限。建议先定义四级内部质量等级：

| 等级 | 典型来源 | 目标行为 |
| --- | --- | --- |
| `realtime` | 高级会员或内部联盟正在进行的普通战或 CWL | 自动高频刷新，独立实时队列，不能被离线任务阻塞 |
| `interactive` | 免费成员主动刷新、首次订阅的核心数据 | 受冷却控制，异步排队，尽快返回新缓存但不承诺实时轮询 |
| `scheduled` | 免费部落夜间资料、都城、竞赛 | 在业务窗口内错峰完成，允许分钟到小时级延迟 |
| `backfill` | 历史补算、原始响应归档、低优先级修复 | 资源空闲时执行，可以暂停和续跑 |

同一资源存在多个联盟需求时，只生成一个 `sync_target`，有效质量取所有未过期需求中的最高等级。高等级需求结束后设置短暂降级宽限期，避免套餐变化、战争状态抖动或多个联盟订阅变化造成频率反复切换。

质量等级只决定采集计划。免费版或普通会员复用了高级会员产生的更新鲜公共缓存，并不获得高级会员可靠性承诺、管理权限或额外功能。

以下细节仍需结合容量压测确定：各等级最大延迟、降级宽限时长、全局请求预算和普通付费套餐的具体频率。

## 7. 采集 Worker 与任务队列模块（核心已实现）

> `sync_interests / sync_targets / sync_tasks / sync_attempts`、live Planner、独立 Worker、
> 四级优先级、租约恢复、有限重试和按资源类型回滚已实现。未来并发度、上游请求预算与扩容阈值
> 仍属于容量观测后再确认的调优参数。

### 7.1 责任

- 封装 COC API 及其他授权数据源的实际请求；
- 按资源类型执行部落、成员、当前战争、CWL、都城和竞赛采集；
- 区分上游无数据、权限拒绝、限流、超时和数据解析错误；
- 采集失败时不把空结果当作新事实覆盖有效数据；
- 产出可重放、可审计的标准化结果；
- 相同部落、资源和有效时间窗口内只允许一个实际采集任务执行。

### 7.2 进程与队列划分

调度规划和任务执行拆开：

```text
同步需求 sync_interests
        ↓
单实例 Planner：合并需求、计算质量和下次执行时间
        ↓
持久化 sync_tasks
        ↓
独立有限并发 Worker 池（按优先级领取）
        ↓
标准化结果与任务状态
```

- `realtime / interactive / scheduled / backfill` 是持久化任务的四级优先级，并非四个必须独立部署的 Worker；
- `realtime` 优先处理活跃战争和 CWL，`interactive` 处理用户手动刷新和首次订阅，`scheduled / backfill` 承载周期与低优先级任务；
- Planner 保持单实例，独立 Worker 有限并发；相同资源依靠数据库幂等键和租约防止重复执行；
- Scheduler 与 Worker 是同一服务器上的独立常驻进程，长耗时任务不再阻塞两分钟级实时检查。

### 7.3 任务状态与幂等

任务状态统一为：

```text
pending → running → succeeded
                  ↘ retry_wait → running
                  ↘ failed / dead
pending / retry_wait → cancelled
shadow 计划另使用 shadowed 终态
```

每个任务记录 `resource_type`、`resource_key`、`priority`、`due_at`、`available_at`、`lease_owner`、`lease_expires_at`、`attempt_count`、`last_error` 和结果时间。当前幂等键以资源、计划时间桶与 payload 版本组合生成。

```text
resource_type + resource_key + 计划时间桶 + payload_version
```

Worker 领取任务时必须原子更新租约；进程异常退出后只有租约过期任务可以重新领取。结果写入使用业务唯一键 upsert，重复执行不能生成重复战争、成员事实或审计记录。

### 7.4 并发、限速与重试

- 当前 Worker 默认并发为 3，代码上限为 8；后续只根据队列延迟、上游限流和 SQLite 写锁指标调整，不以提高 CPU 利用率为目标；
- 按供应商、Token/IP、资源类型和部落实行分层限速；用户手动刷新不能拥有独立的无限预算；
- HTTP 429 尊重 `Retry-After` 并降低对应上游并发，不能立即重试；
- 网络超时和 5xx 使用带抖动的指数退避；认证失败、权限拒绝和确定的参数错误不盲目重试；
- `notInWar`、尚未开始、没有数据和请求失败必须是不同业务状态；
- 连续失败达到上限后进入 `dead`，保留旧缓存并告警，人工或恢复探针确认后再重新排队；
- 原始错误需要分类和脱敏，不能记录 Token、完整授权头或用户隐私。

### 7.5 数据源权威性

当前资料和当前战争优先使用 COC 官方 API；本地结构化事实是页面查询和统计的权威来源。历史回填只使用项目已经授权和明确允许的数据源，不因为扩展免费用户增加未授权抓取。外部历史结果不得覆盖更新、完整且来源更高优先级的本地最终事实。

Worker 并发数、各上游预算、最大重试次数和熔断窗口均为运行参数，正式值需要压测和灰度数据确认。

### 7.6 M4.0 历史归档：影子规划边界

M4.0 已按本章模型建立持久化需求、目标、任务和尝试表，并实现全局资源去重、四级优先级、任务幂等、
原子有限领取、租约恢复和有限退避。当前 Planner 只从本地 `alliance_clans`、
`alliance_cwl_seasons / alliance_cwl_teams` 与战争缓存计算计划，生成的任务固定为影子模式；没有真实
Worker、外部请求或业务事实写入。影子调度开关默认关闭，旧调度器继续承担全部生产同步。

本小节仅记录 M4.0 当时的影子阶段，不代表当前运行状态。后续 M4 已完成 live Planner、
Worker 四类资源接管与生产回滚演练，当前行为见 `docs/15-scheduler.md`。Worker 并发和扩容阈值仍需按生产容量指标调整，
不等于对外 SLA 已经确认。

## 8. 数据存储与缓存模块

### 8.1 责任

- 区分公共游戏事实、联盟私有数据和运行状态；
- 将公共事实按部落 Tag、玩家 Tag 和战争唯一键全局去重；
- 对联盟成员关系、角色、标签、备注、名单、管理评价和套餐数据按 `alliance_id` 隔离；
- 持久化保存 `alliance_id + clan_tag` 的订阅关系和认证状态，包括申请人、审核人、审核时间、状态和备注；
- 普通联盟认证入口不允许覆盖其他联盟已有认证；超级管理员可在平台人工入口建立多联盟认证，
  并保留联盟和平台双重审计；
- 允许多个联盟以未认证状态订阅同一个部落，并复用同一份公共事实；
- 为高频前端读取提供缓存或预计算结果；
- 缓存键必须包含足够的联盟和权限上下文，禁止将管理字段混入公共缓存；
- 保留数据更新时间、数据源、成功状态和错误来源。

### 8.2 历史保存与冷热分层

**已讨论确认：**免费与付费暂时使用相同的数据保存规则。结构化的普通战、CWL、都城、竞赛和成员统计事实可以长期保存，不能因为套餐不同而为同一个公共事实生成多份副本，也不应把缩短免费历史作为当前容量治理手段。

**建议草案（未逐项讨论）：**随着部落数量增长，容量治理优先针对占用更大的原始响应，而不是删除用户可见的结构化历史：

1. 已结束战争的结构化结果和成员事实继续保留；
2. 完整战争原始 JSON 只在热存储中保留必要的调试和重算窗口；
3. 超出热存储窗口的原始 JSON 可以压缩或迁移到对象存储；
4. 页面查询统一读取结构化事实或预计算结果，不依赖长期保存在主数据库中的完整原始响应；
5. 冷热分层、归档期限和恢复流程在部落规模增长前通过容量测试确定。

因此，“免费与付费保存相同历史”指用户可见历史、结构化统计和查询窗口保持一致，不要求主 SQLite 永久保存所有外部 API 原始 JSON。

### 8.3 建议的数据模型

新增模型按职责分组，避免把联盟私有关系混入现有公共游戏事实：

| 模型 | 关键身份 | 用途 |
| --- | --- | --- |
| `alliances` | `alliance_id` | 名称、状态、创建者和默认配置 |
| `alliance_members` | `alliance_id + user_id` | 角色、成员状态、加入和退出时间 |
| `alliance_plans` | `plan_code` | 套餐模板、部落配额、同步等级和功能权益 |
| `alliance_clans` | `alliance_id + clan_tag` | 订阅状态、业务标签、加入和移除时间 |
| `alliance_share_links` | 随机分享摘要 | 来源联盟、创建者、可见范围、状态、次数和过期时间 |
| `alliance_plan_grants` | 权益记录 ID | 联盟人工套餐权益、开始/到期时间、状态和操作人 |
| `platform_admins` | `user_id` | 平台管理员唯一授权来源；免费灰度环境白名单不能授予平台权限 |
| `platform_settings` | 设置键 | 免费注册开关和总配额等平台级设置 |
| `platform_audit_events` | 事件 ID | 人工认证、套餐、联盟状态和平台设置审计 |
| `sync_interests` | 联盟 + 资源 | 各联盟对公共资源的质量需求 |
| `sync_targets` | 资源唯一键 | 合并后的有效质量、下次执行和最后成功状态 |
| `sync_tasks` | 任务 ID | 持久化队列、优先级、租约、重试和幂等键 |
| `sync_attempts` | 任务 ID + 次数 | 单次执行耗时、结果、错误分类和请求计数 |
| `alliance_audit_events` | 事件 ID | 成员、角色、认证、套餐、分享和部落变更审计 |

现有 `accounts`、战争、CWL、都城和竞赛事实继续以玩家 Tag、部落 Tag、战争键和 period 为公共身份，不增加 `alliance_id` 副本。只有角色、备注、归属、人工判断、认证、名单和管理决策等私有数据携带 `alliance_id`。

### 8.4 存储演进建议

1. **灰度阶段**：保留 SQLite，启用并验证 WAL、短事务、必要索引和单一任务 Planner；任务领取必须使用原子事务。
2. **扩大阶段**：在约 20、50、100 个外部部落节点分别压测并复核写锁等待、API P95、队列积压、备份耗时和数据库增长。
3. **迁移 PostgreSQL**：在需要多机 Worker、持续出现写锁等待、数据库达到数 GiB、备份窗口不可接受，或准备大规模正式开放前迁移；不以单一部落数量作为唯一门槛。
4. **引入 Redis**：只在多进程或多机需要共享短期缓存、分布式锁、限速计数器时引入；联盟、权限、认证和任务最终状态不能只存在 Redis。
5. **对象存储**：用于压缩后的原始战争响应、归档和备份；页面读取继续使用结构化数据库，不直接扫描对象存储。

迁移使用双写校验或停写窗口、全量校验、增量追平和可回滚切换。任何数据库迁移都必须先验证备份可恢复，不能在请求路径临时执行 DDL。

### 8.5 尚未确认

- PostgreSQL 的最终部署方式、分区键和连接池参数；
- 原始 JSON 在热存储中的具体保留天数；
- 联盟删除后的私有数据恢复窗口和法务删除边界；
- 认证移交时旧联盟私有备注是否允许导出或交接。

## 9. API 与读取模块（核心已实现）

> 当前路由、权限和响应字段以 `docs/10-api-server.md` 和代码为准。本章的统一响应状态格式、
> 游标分页和新的 API 版本策略仍属于未实现草稿。

### 9.1 责任

- 所有联盟相关请求都显式携带当前 `alliance_id`；
- 所有涉及具体部落的数据请求还必须明确携带 `clan_tag`；
- 对用户身份、联盟成员关系、联盟角色、`alliance_id + clan_tag` 认证状态和套餐权益分别校验；
- 未认证部落的业务数据权限统一封顶为联盟成员，即使请求者是联盟创建者、管理员或首领；
- 已认证部落只有联盟管理员和联盟首领可以读取或操作管理数据；
- 只返回当前用户、联盟和部落可见的字段，不用前端隐藏代替数据权限；
- 高频读取优先返回缓存或预计算结果；
- 响应显式返回数据新鲜度、降级或部分失败状态。

### 9.2 API 边界

建议按当前联盟和部落范围组织接口，不允许客户端依赖全局配置推断访问范围：

```text
/api/alliances
/api/alliances/{alliance_id}
/api/alliances/{alliance_id}/members
/api/alliances/{alliance_id}/clans
/api/alliances/{alliance_id}/clans/{clan_tag}/...
/api/shares/{share_token}
```

- 列表接口只返回当前用户可访问的联盟；
- 联盟内批量接口先逐部落计算认证和角色权限，再合并响应，不能以“联盟管理员”一次放行所有部落；
- 公共字段、成员字段、管理字段使用服务端序列化模型分开定义，不能先返回完整对象再由前端隐藏；
- 管理接口不接受前端传入的角色或认证结论，只接受资源身份和业务参数；
- 页面请求读取缓存与结构化事实，手动刷新只创建后台任务并返回任务状态。

### 9.3 统一响应状态

涉及外部数据的响应建议附带：

```json
{
  "data_status": "fresh | stale | partial | unavailable",
  "updated_at": "...",
  "refresh_status": "idle | queued | running | failed",
  "retry_after_seconds": 0
}
```

没有数据、尚未同步、部分同步、缓存过期和同步失败必须分别表达。旧缓存仍然可用时返回 `stale`，不能因为本次请求失败返回空数组覆盖页面。

### 9.4 查询与缓存

- 大成员表、跨部落排序、审计记录和任务列表使用后端分页、排序和筛选；
- 游标优先用于持续增长的历史事实，稳定小表可以使用页码；
- 缓存键至少包含 `alliance_id`、`clan_tag`、权限级别、查询版本和筛选参数；
- 公共事实缓存不包含联盟私有字段，管理缓存必须随成员角色、认证和联盟切换立即失效；
- 客户端切换联盟时取消或丢弃旧 `alliance_id` 的迟到响应。

### 9.5 版本与灰度

多联盟接口使用独立版本或显式能力标记，与当前单联盟接口并行灰度。旧客户端不得因为缺少 `alliance_id` 意外读取默认联盟的管理数据。接口迁移完成前保留兼容层，但兼容层只服务当前苍穹范围，不作为新联盟入口。

### 10.1 责任

- 本轮部落认证由平台管理员人工完成，作者微信 `pluto1944606` 作为申请入口，并对每个部落的审核结果留下审计记录；

- 分享链接只传递联盟入口或受限资源上下文，不传递管理员、首领或认证权限；
- 对管理员设置、成员移除、认证移交、套餐变更和联盟配置变更留下审计日志；
- 对 Token、密钥、个人信息和原始外部数据实施最小化保存；
- 支持封禁、撤销分享、撤销认证和紧急关闭高风险功能。

### 10.2 人工认证现状与未来挑战认证草稿

**当前已实现：**前端保留认证按钮，只显示人工处理说明；后端没有生成、校验
或轮询验证码的接口。平台管理员可以人工设为已认证、争议、撤销或未认证，数据库触发器和业务校验
阻止普通用户覆盖其他联盟已有认证；超级管理员可在平台入口显式建立多联盟认证，不自动撤销原关系。

**未来草稿（未实现，实施前需重新讨论确认）：**

- 创建认证挑战时生成一次性随机码，绑定 `alliance_id + clan_tag + applicant_user_id`，默认 30 分钟过期；
- 介绍挑战要求官方 `description` 包含本次验证码；预设 `labels` 不包含随机内容，不作为独立认证条件；
- 验证操作按用户、联盟和部落限频，不在后台持续高频轮询；
- 成功后只保存验证码摘要、验证方式、时间和官方响应哈希，不长期复制完整部落介绍；
- 认证冲突、官方接口异常和无法完成自动挑战时转人工微信审核。

### 10.3 认证冲突与自助移交

**当前已实现：**普通用户、联盟管理员和首领无权覆盖已有认证，冲突和移交统一联系超级管理员人工处理。
平台可在不撤销原关系的情况下显式建立多联盟认证，也可进入各联盟逐个撤销；操作同时写入联盟审计和平台审计。

**未来草稿：**由当前认证联盟首领发起、目标联盟首领接受的自助移交未实现，实施前需重新讨论确认。

以下自助移交实现细节属于**未来草稿（未实现）**：

- 目标联盟必须已经订阅同一 `clan_tag`，且接受移交后不能突破 10 个部落配额；
- 移交请求使用不可预测一次性令牌并设置有效期，只允许目标联盟首领接受；
- 接受前原联盟保持认证，原联盟首领可以撤销请求；
- 接受时使用事务原子撤销原认证并创建目标认证，任何一步失败都保持原归属；
- 成功后原联盟立即失去该部落管理权限，相关私有数据不自动复制给目标联盟；
- 全流程记录新旧联盟、发起人、接收人、部落、时间和前后状态；
- 原联盟无法操作、重复申请、双方争议或疑似盗号时禁止自助覆盖，进入人工申诉。

### 10.4 分享与访问安全默认值

- 联盟加入链接默认 30 天、资源分享默认 7 天，具体期限可配置；
- 分享令牌至少使用 128 bit 不可预测随机值，数据库保存摘要并支持撤销；
- 分享解析、加入和资源读取分别限频，过期、撤销或错误令牌不泄露联盟是否存在；
- 未登录分享页只返回公开白名单，不创建成员、不触发同步、不读取管理缓存；
- 登录后加入只创建普通成员关系，分享者角色和认证状态不传递；
- 被移除或封禁用户不能依靠旧链接自动恢复。

本轮实现值为：联盟邀请 1～30 天、默认 30 天；每联盟最多 5 个有效邀请、每邀请最多使用 1000 次；
正式加入的联盟不设总数上限，浏览历史最多保留 50 个；每用户每天最多通过分享主动新加入 20 个。原始令牌只在创建时返回，数据库保存
SHA-256 摘要；预览与加入接口用 POST 请求体传令牌，未登录预览不创建成员或同步任务。

### 10.5 审计范围

下列操作必须写入不可由普通业务接口修改的审计事件：

- 联盟创建、改名、停用、删除和首领移交；
- 成员加入、退出、移除、封禁、解封和角色变化；
- 部落添加、更换、移除、认证申请、审核、争议、移交和撤销；
- 套餐购买、续期、降级、配额变化和人工补偿；
- 分享链接创建、撤销和异常访问处置；
- 管理数据导出、批量修改和人工数据修正；
- 同步策略、功能开关和紧急降级的管理员操作。

审计事件至少记录操作者、联盟、目标资源、动作、前后状态摘要、时间、请求追踪 ID 和来源。敏感字段只记录必要摘要，不能把 Token、完整外部响应或私人资料复制进审计日志。

### 10.6 仍需业务确认

- 联盟删除、用户销户和隐私数据删除的具体期限；
- 首领能够查看到何种粒度的安全审计和成员访问记录。

## 11. 可观测性与可靠性模块（基础已实现，告警阈值为草稿）

### 11.1 责任

- 监控任务积压、同步延迟、执行时长、错误率和 API 消耗；
- 按资源类型、质量等级、联盟套餐和部落追踪数据新鲜度；
- 对付费联盟部落的同步超时和连续失败优先告警；
- 区分上游无数据、缓存过期、任务失败和系统容量不足；
- 为计费、容量规划和故障复盘保留必要的指标；
- 公共采集任务被多个联盟复用时，记录需求来源和最终采用的最高质量等级。

### 11.2 最小指标集

至少按供应商、资源类型、质量等级和任务队列记录：

- 请求次数、成功率、HTTP 状态码、429 数量、超时和平均/P95/P99 耗时；
- 队列长度、最老任务等待时间、任务执行时长、重试次数和死信数量；
- 各部落最后成功时间、数据年龄、连续失败次数和当前有效质量等级；
- SQLite/PostgreSQL 写入耗时、锁等待、慢查询、数据库体积和备份耗时；
- Worker 存活、租约过期、重复任务抑制和 Planner 单实例状态；
- 磁盘、内存、CPU、文件描述符和进程重启次数。

当前只记录任务总耗时不足以支持扩容判断。所有外部客户端应通过统一埋点层产生请求指标，禁止各模块自行采用不一致口径。

### 11.3 初始告警建议

- `realtime` 队列最老等待超过目标刷新周期两倍；
- 外部 API 429 或超时率在短窗口持续升高；
- 活跃战争连续两轮没有成功更新；
- 最终归档超过结束时间 30 分钟仍未成功；
- 死信任务出现、Planner 多实例、任务租约大量过期；
- 数据库或磁盘可用空间低于安全阈值、备份连续失败；
- 同一部落或用户短时间产生异常多的手动刷新或分享访问。

免费版只承诺展示真实数据时间和状态，不承诺严格 SLA。未来付费 SLA、新鲜度阈值和对外赔付不在技术文档中擅自确定。

## 12. 容量保护与降级模块（基础已实现，扩容阈值为草稿）

### 12.1 基本原则

资源紧张时应优先保障付费联盟的活跃战争，再保障付费联盟的普通同步，最后处理免费联盟的低质量订阅。降级只能降低时效性或使用旧缓存，不能混淆联盟数据或把失败写成空数据。

建议的优先级骨架：

```text
P0  付费联盟正在进行的部落战 / CWL
P1  付费联盟准备日与核心成员数据
P2  付费联盟普通资料和历史补全
P3  免费联盟订阅部落的低频资料
P4  可延迟的历史补算与离线统计
```

当免费联盟和付费联盟订阅同一部落时，公共数据只执行一次，并采用付费联盟要求的较高质量；这不自动提高免费联盟的刷新可靠性、管理权限或其他套餐权益。双方读取同一份去重后的公共历史。

### 12.2 降级顺序

资源紧张或上游异常时按以下顺序降级：

1. 暂停历史回填、原始 JSON 归档和非必要重算；
2. 延后免费部落夜间资料、都城和竞赛任务，但保留最终归档；
3. 延长免费手动刷新冷却并限制新初始化任务；
4. 降低准备日和无战争状态探测频率；
5. 保留付费活跃战争、最终归档、登录和权限校验；
6. 上游全面故障时全部页面使用旧缓存并明确标记，不继续制造重试洪峰。

任何降级都不能放宽鉴权、跨联盟混用私有数据，或用空结果覆盖上次成功数据。

### 12.3 准入与熔断建议

- 灰度期设置全局免费部落配额，达到配额后允许排队申请但不立即创建新的同步目标；
- 单部落连续失败时只熔断该资源，不阻塞其他部落；
- 单供应商 429/5xx 达到阈值时熔断对应上游，延迟恢复探针而非所有任务立即重试；
- `realtime` 队列持续积压、最终归档超时或磁盘剩余不足 20% 时暂停接收新免费订阅；
- 磁盘剩余不足 10%、数据库完整性异常或备份失败时停止非关键写入并人工处置；
- 新增部落只能使用公共容量预算，不能挤占苍穹和已付费联盟的保留容量。

具体错误率、持续窗口、并发上限和最大延迟必须通过压测与灰度确认，以上仅为默认保护方向。

## 13. 迁移与上线模块（M0～M9 技术阶段已归档）

> 以下阶段 0～3 已完成；外部免费扩容、真实付费试点和正式商业开放尚未执行，仍属于待业务确认的后续计划。

### 13.1 分阶段方案

1. **阶段 0：可观测性基线**。先补外部请求、队列延迟和数据新鲜度指标，不改变生产业务。
2. **阶段 1：苍穹租户化**。把现有配置映射为第一个内部联盟，引入 `alliance_id` 和权限解析，但页面与刷新行为保持不变。
3. **阶段 2：同步解耦**。引入 `sync_interests / sync_targets / sync_tasks`，拆分实时和离线 Worker，用现有十二个部落验证去重、租约、重试和回滚。
4. **阶段 3：内部灰度**。让测试账号创建免费联盟，验证订阅、切换、分享、认证、字段权限和首次初始化，不开放公众入口。
5. **阶段 4：外部免费灰度**。先开放约 20 个免费部落；指标稳定后扩到 50、100 个，每次扩容前复盘请求量、队列和数据库增长。
6. **阶段 5：付费试点**。接入一个外部付费联盟，逐部落认证，验证实时刷新、可靠性、权限隔离和降级。
7. **阶段 6：正式开放**。只有容量压测、备份恢复、上游故障演练和权限安全测试全部通过后才扩大范围。

### 13.2 上线门槛

- 苍穹现有功能和同步时效不回退；
- 联盟数据隔离和逐部落权限有自动化测试；
- 同一部落公共数据去重与最高质量合并有自动化测试；
- 队列积压、同步延迟和上游限流可观测；
- 新免费联盟或付费联盟不会绕过配额和容量保护；
- 未认证部落无法通过角色、分享或参数修改获取管理数据；
- 存在已验证的数据备份、回滚和降级方案。

### 13.3 回滚原则

- 多联盟新表和接口以增量方式引入，不直接改写现有苍穹事实表的业务身份；
- 新旧接口并行灰度，功能开关可以按用户、联盟和部落关闭；
- 队列异常时可以停止 Planner 和新 Worker，恢复当前苍穹调度路径；
- 数据迁移必须有行数、唯一键、抽样字段和权限结果校验；
- 回滚不能删除灰度期间已经产生的战争最终事实和审计记录；
- 任何阶段只要苍穹时效下降、出现越权或最终归档不完整，立即停止扩容并回退入口。

## 14. 跨模块不变量

条目 1～23、29、31 为当前**已讨论确认且已实现**的原则。条目 24 中的公共历史去重已经确认，原始 JSON 归档方式仍是**建议草案**。条目 25～28 中，基础资料、成员、当前战争的异步初始化已实现，完整免费刷新时间表仍是**建议草案**。条目 30、32 记录当前人工流程；自助验证码和自助移交另列为未来草稿。

1. 系统只有联盟这一种租户实体，免费和付费通过套餐权益区分；
2. 每个用户最多创建并拥有 1 个免费联盟，默认名为“我的部落”，最多订阅 3 个部落；
3. 免费联盟和付费联盟共用联盟、成员、角色、分享和逐部落认证模型；
4. 免费联盟升级为付费联盟时必须保留 `alliance_id`、成员、角色、分享关系、认证记录和历史；
5. 相同部落的公共数据全局去重，按最高有效同步质量采集；
6. 联盟私有数据必须携带 `alliance_id`，不得通过公共缓存泄露；
7. 任何页面请求不直接触发外部批量采集；
8. 采集失败时保留上次有效数据，并明确标记失败与新鲜度；
9. 套餐权益不等于管理权限，联盟角色不等于部落认证，同步质量也不等于数据可见范围；
10. 部落认证以 `alliance_id + clan_tag` 为单位，不能用联盟整体认证代替；
11. 未认证部落的业务数据权限统一封顶为联盟成员；
12. 只有当前联盟已认证当前部落，且当前用户是联盟管理员或首领时，才能查看该部落管理数据；
13. 会员联盟添加的每个部落都必须分别认证，不能继承其他部落或其他联盟的认证；
14. 同一 `clan_tag` 可被多个联盟订阅；普通认证不允许覆盖已有认证，超级管理员可在平台入口显式允许多联盟认证；
15. 苍穹联盟作为首个迁移联盟，不能被新用户的负载拖低服务质量；
16. 部落标签只控制默认页面、默认列和专项统计，不控制认证、角色、套餐或真实战争发现；
17. 免费联盟的 `combat=战营` 内部语义必须与普通用户的 `normal=实战` 标签分离；
18. 未建立外部数据来源前，不向免费互刷部落伪造或默认开放填坑号名单；
19. 免费版和普通会员的实时战况以按需刷新为主，但普通战和 CWL 的低频状态探测、时间点调度与最终归档必须自动执行；
20. 手动刷新只提交可去重、可限频的后台任务，不允许页面请求直接阻塞调用 COC API；
21. 免费部落不执行每日全成员详情扫描，基础成员字段复用部落成员列表，逐玩家详情只用于竞赛月结、绑定认证、异常补数及未来明确启用的详细档案功能；
22. 高级会员和内部版可执行高质量成员详情刷新；免费版和普通会员不执行日常逐成员扫描；
23. 免费与付费暂时采用相同的用户可见历史范围和结构化数据保存规则，套餐差异不通过缩短免费历史实现；
24. 相同部落的公共历史全局去重；容量增长时优先归档原始 JSON，不删除仍需查询的结构化事实；
25. 首次订阅只同步提交初始化计划，页面请求不能直接阻塞执行外部批量采集；
26. 首次订阅优先取得部落资料、成员列表和当前战争状态，历史回填异步执行，已有公共缓存直接复用；
27. 首次订阅不触发全成员详情扫描、竞赛结算或持续高频战争轮询；
28. 免费部落按统一时间表执行：基础资料和成员每 24 小时一次，普通战/CWL 每 6 小时发现并按开始、结束边界确认；都城每周二一次、竞赛每月 29 日一次，互刷与活动统计复用已采集事实，不产生独立重复请求；
29. 普通会员和高级会员最多订阅 10 个部落，每个部落分别认证；
30. 当前部落认证由平台后台人工处理；介绍验证码只是未来草稿，未实现；
31. 普通会员和高级会员不按部落数量分档，两者均为 10 个；高级会员增加后台高频自动刷新；
32. 认证冲突和正常移交当前都由超级管理员人工处理；双方首领自助移交属于未来草稿，未实现。

| Worker、持久化队列和质量等级 | 已实施基础能力 | M4 已接管四类公共资源，参数仍需按容量调整 |
| 多联盟数据库、API、安全和审计 | 已部署基础能力 | M1～M9 后端技术底座已落地并通过自动化验收；前端待微信发布 |
| 监控、容量熔断和灰度步骤 | 建议草案（未逐项讨论） | 20/50/100 部落仅为建议的观察节点 |
| 原始 JSON 冷热分层和对象存储 | 建议草案（未逐项讨论） | 用户可见历史一致已经确认，存储实现尚未确认 |

### 15.2 已确认方向中的待细化建议

以下条目同时列出已经确认的方向和仍待实施前复核的细节。条目中明确写为“已经确认”的内容不是建议草案，其余参数与交互仍按**建议草案（未逐项讨论）**处理：

1. **免费联盟更换部落**：暂建议每 7 天最多更换一次；更换后旧部落退出当前联盟页面，但公共历史不删除；是否提供短时撤销、联盟成员确认和特殊申诉尚未讨论。
2. **未来会员商业化**：普通会员和高级会员均最多 10 个部落已经确认；价格、有效期、支付续费方式和服务承诺尚未讨论。
3. **调度与任务队列**：四级优先级、全局去重、持久化任务、租约、退避、死信和独立 Worker 已实现；未来并发度、限速器和扩容阈值仍需按生产指标调优。
4. **多联盟数据库结构**：联盟、成员、订阅、套餐权益、分享、同步任务和平台审计已经落地；公共事实按 Tag 全局去重，私有管理数据带 `alliance_id`。
5. **分享与加入细节**：分享者权限不传递、新加入者为普通成员；30 天默认有效期、撤销、摘要保存、未登录预览和登录加入已经实现。
6. **认证生命周期**：部落介绍验证码方案仍保留为未来方向；本轮按用户决定只实现平台人工认证，冲突与移交也先人工处理。
7. **灰度与容量保护**：建议先开放约 20 个免费部落，观察队列延迟、外部 API 成功率、429、任务积压和数据库增长，再分阶段扩大到 50、100 个；具体门槛尚未讨论。

### 15.3 后续工作方式

任务队列、多联盟数据库、缓存读取、API 权限、基础监控和技术灰度底座已实现。仍以**建议草案**管理的是完整免费刷新时间表、告警阈值、扩容节点、对象存储策略与商业 SLA。正式收费前还需确定：

1. 普通会员与高级会员的价格、有效期、支付与续费方式；
2. 是否提供对外 SLA、故障补偿或退款规则。

在上述商业事项尚未确认前，可以实施不改变生产行为的可观测性、公共任务抽象和自动化测试；不能提前开放收费、扩大外部联盟入口或改变现有苍穹权限。

## 16. 实施门槛

### 16.1 可以先实施的基础工作

以下工作不依赖套餐价格、最终权限边界或认证争议规则，可以在详细代码设计和用户明确授权后先行实施：

- 外部 API 请求次数、429、耗时和成功率指标；
- 数据新鲜度、队列延迟和最终归档监控；
- 公共资源键、任务幂等键和错误分类的纯函数与测试；
- 现有苍穹配置到只读联盟模型的迁移演练；
- 权限解析器和字段白名单的测试框架，但暂不改变生产返回字段；
- 数据库迁移、备份恢复和回滚的离线演练。

### 16.2 已实现但需发布、业务验收或显式开关后才能生效

- 公开分享加入和外部免费联盟入口；
- 普通成员与管理员历史评价字段分级；
- 平台人工部落认证和管理权限启用；
- 平台后台和免费注册总配额。

**未实现或待讨论：**免费联盟更换部落、自助验证码、自助认证移交、付费价格、在线支付与续费、SLA 和正式付费商业开放。

### 16.3 禁止直接从草案推导上线行为

所有标记为“建议草案（未逐项讨论）”的数字和策略，包括 7 天更换冷却、30 天标签冷却、分享期限、Worker 并发 3～5、20/50/100 部落灰度以及存储迁移阈值，都需要在对应实施批次开始前集中复核。未经复核，不得仅因其写入本文档就视为用户已批准上线。
