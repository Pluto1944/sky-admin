# CWL 集结检查设计

## 1. 目标与范围

“集结检查”位于小程序 `战斗 -> 联赛点名 -> 集结检查`，用于每月联赛开启前核对正式名单与各联赛部落当前成员：

- 正式名单中且已在对应部落：正常色；
- 正式名单中但未在对应部落：红色；
- 不在正式名单但出现在该部落：绿色。

第一层展示当月全部联赛部落的汇总卡片，点击卡片后在当前 TabBar 页面内打开单部落详情，并保留底部四个主导航。详情展示昵称、职位和大本等级；COC 官方接口不提供最近登录时间，本版不展示该字段。

本功能只做集结核对，不改变报名、编排、正式名单发布或 CWL 战斗日数据。

## 2. 权威来源与快照规则

### 2.1 正式名单

正式名单唯一来源是 `PUBLISH_DOC_FILE_ID` 指向的腾讯文档正式发布子表，不能以 `registrations.team_info` 或当前配置代替。目标子表名按月份生成，例如 `2026-10` 对应 `26.10月联赛 报名结果`。

北京时间每月 1 日 14:00 起尝试生成当月正式名单快照：

1. 读取正式发布子表；
2. 解析部落标题行、部落标签与其后的成员单元格；
3. 使用当月 `league_teams` 校验部落集合；
4. 全部校验通过后一次性写入快照；
5. 失败时不写入半成品，5 分钟后重试；
6. 当月首次成功快照自动锁定，后续调度不再读取在线文档。

在线文档在快照后再次编辑不会自动影响检查结果。需要纠错时只能显式执行强制重建，生成新 revision 并保留旧 revision；普通读请求不得触发文档读取或快照重建。

Part4 抬头同时保存 `leader_name` 和 `manager_names`：`leader_name` 是发布时由 COC 返回的完整首领昵称，和 `league_teams.leader` 配置简称代表同一人，正式表为空时先回退配置简称；两者都为空时，快照生成任务仅为该部落补查一次 COC 官方资料。`manager_names` 是当月联赛管理，可包含多人。小程序“联赛数据”卡片按“首领：…　联赛管理：…”同一行展示。

正式表未填写管理时，`manager_names` 保持为空，页面显示 `-`，不能把当月人员硬编码到小程序或 `league_teams`。业务明确确认补录值后，应以新的名单 revision 写入月度快照，并让现有集结缓存换绑新 revision；只修改首领或管理元数据时不得重新计算已经冻结的成员检查结果。

强制生成新 revision 时先比较部落标签和正式成员序列。若它们没有变化、只有首领或管理等抬头元数据变化，则只换绑缓存的 revision，保留已冻结的集结结果；只有正式成员发生变化时才重新核对。

### 2.2 当前部落成员

名单快照成功后，调度任务按部落调用 COC 官方成员接口，缓存昵称、玩家标签、职位和大本等级。页面请求只读本地缓存，不直接调用 COC。

单个部落的一轮顺序固定为：

1. 拉取当前成员；
2. 与正式名单比较并写入最新成功结果；
3. 查询该部落当月 CWL 联赛组；
4. 若确认当月联赛已经开启，则把本轮结果冻结为最终集结状态。

网络或接口失败时保留上一次成功数据并记录错误，不能以空列表覆盖，也不能误判为已经集结或已经冻结。

## 3. 时间窗口与停止条件

调度任务 `cwl_assembly` 每 5 分钟执行一次，但仅在北京时间的业务窗口内做外部请求：

- 开始：每月 1 日 14:00；
- 部落级停止：检测到该部落当月 CWL 联赛组后立即冻结；
- 全局停止：每月 3 日 16:00；仍未开启的部落冻结为“截止时未开启”；
- 窗口外：只返回 skipped，不读取腾讯文档或 COC。

若服务在 1 日 14:00 后才恢复，只要仍处于窗口内且当月没有有效快照，就立即补做首次快照。手动 `--force` 可在窗口外做指定月份的恢复操作，但不能成为日常调度路径。

## 4. 名称匹配规则

第一版只按昵称、逐个部落精确匹配：

- 去掉昵称首尾空白；
- 不忽略大小写，不删除 emoji、符号或中间空格；
- 壳子名单单元格可去除系统附加的末尾匹配分值；
- 不做模糊匹配，也不借助玩家标签猜测；
- 重名按出现次数进行多重集合匹配，不能用普通集合吞掉重复项。

成员被分配到 A 部落却在 B 部落时，会自然表现为 A 的红色缺席和 B 的绿色额外成员，本版不增加“去了错误部落”的第四种状态。

## 5. 数据模型

### 5.1 `cwl_roster_snapshots`

保存正式名单的不可变 revision：

| 字段 | 含义 |
| --- | --- |
| `id` | 快照主键 |
| `period` | 联赛月份 `YYYY-MM` |
| `revision` | 月内版本号，从 1 开始 |
| `is_active` | 当前生效 revision |
| `source_sheet` | 来源子表标题 |
| `content_hash` | 规范化内容哈希 |
| `data_json` | 各部落、首领、联赛管理及正式成员顺序 |
| `created_at` | 成功生成时间 |

每个月只能有一个生效快照。新 revision 在完整解析与校验后以事务切换，避免读到半成品。

### 5.2 `cwl_assembly_cache`

每月、每部落一行：

| 字段 | 含义 |
| --- | --- |
| `period`, `clan_tag` | 联合主键 |
| `roster_snapshot_id` | 使用的正式名单快照 |
| 队伍元数据 | `team_index/team_alias/team_name/category` |
| `status` | `checking/started/cutoff/error` |
| `data_json` | 本轮正常、缺席、额外成员及汇总 |
| `error` | 最近一次失败原因 |
| `updated_at` | 最近成功同步时间 |
| `attempted_at` | 最近尝试时间 |
| `locked_at` | 冻结时间，未冻结为空 |

已冻结行不再请求 COC。失败只更新 `error/attempted_at`，保留 `data_json/updated_at`。

## 6. API

所有接口沿用当前联赛页面的公开只读权限：

- `GET /api/clan/cwl-assembly`：返回当月快照状态、全队汇总卡片和更新时间；
- `GET /api/clan/cwl-assembly/{clan_tag}`：返回单部落详情，仅允许当月 `league_teams` 中的部落标签。

接口只读 SQLite 缓存。尚未生成快照时返回明确的 `waiting_roster` 状态；无数据、同步失败和缓存陈旧必须可区分。

## 7. 小程序交互

进入“集结检查”时读取汇总接口，此后每 60 秒读取一次本地缓存接口；切换到“出刀提醒”时不清空已有集结数据。

汇总卡片显示：

- 完整部落名、业务名与类别；
- 正式人数、已到位、未到位、额外成员；
- 检查中、已冻结、截止未开启或数据异常；
- 最近成功更新时间。

详情顺序为：未到位（红）-> 额外成员（绿）-> 正常成员（默认色）。当前成员可显示职位和大本等级；未到位成员无法从当前部落接口取得这两个字段，因此显示 `-`。详情顶部提供“返回全部部落”。

## 8. 验证与运维

实现需覆盖：

- 正式表解析、壳子分值清理、重名多重集合匹配；
- 快照成功锁定、失败不落半成品、强制 revision；
- 逐部落失败隔离、旧缓存保留、开启后冻结、3 日 16:00 截止；
- 汇总与详情 API；
- 小程序真实构建。

生产启用前先备份 `data/league.db`，再由 schema 幂等迁移创建新表。部署后检查 `sync_jobs.cwl_assembly`、当月快照、12 个部落缓存行以及 API 返回；不要把数据库、构建产物或腾讯文档凭证提交到 Git。
