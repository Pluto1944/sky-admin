# 部落成员列表与最近数据活动设计

> 状态：第一版已实现。活动时间是公开数据变化估算，不等于官方登录时间。

## 1. 目标与边界

部落主页“成员”用于跨自有部落查看玩家信息，后续可按单一维度排序，辅助识别长期不活跃账号。

COC 官方 API 不提供精确的登录时间。本功能只记录系统最后一次检测到玩家公开数据发生有效变化的时间，页面统一称为“最近数据活动”，不得写成“上次登录”或据此断言玩家当时一定在线。

ClashPerk 等第三方最近活动接口暂不接入。第一版只使用本系统拉取并缓存的官方 COC 数据，以及普通部落战、CWL 的本地事实。

## 2. 成员表列

成员宽表按以下顺序展示：

| 顺序 | 列名 | 数据来源 | 说明 |
|---:|---|---|---|
| 1 | 昵称 | `accounts.account_name` | 游戏昵称 |
| 2 | 玩家标签 | `accounts.player_tag` | 显示完整 `#XXXX` |
| 3 | 部落 | `accounts.clan_tag` + 配置名称 | 当前所在自有部落 |
| 4 | 职位 | `accounts.clan_role` | 首领 / 副首领 / 长老 / 成员 |
| 5 | 大本 | `accounts.town_hall_level` | 大本营等级 |
| 6 | 联赛 | `accounts.league_name` | 主世界联赛段位 |
| 7 | 奖杯 | `accounts.trophies` | 仅展示主世界奖杯，不参与活跃判断 |
| 8 | 赛季进攻 | 玩家详情 `attackWins` 缓存 | 当前赛季联机进攻胜场；赛季归零 |
| 9 | 赛季捐兵 | `coc_raw.donations` | 当前赛季捐出数量 |
| 10 | 赛季收兵 | `coc_raw.donationsReceived` | 当前赛季收到数量 |
| 11 | 部落战近15场 | 自有部落普通战事实派生汇总 | 最近 90 天内，跨全部自有部落最近最多 15 场参战普通战的进攻三星率和样本；第一行显示三星率，第二行按“`15/15（共26刀）`”格式展示三星样本和理论可用刀数，不展示出刀率 |
| 12 | 联赛近3月 | `league_results` 派生汇总 | 最近 3 个完整联赛月内，跨全部自有联赛队伍的进攻三星率和样本；第一行显示三星率，第二行显示“`三星次数/统计进攻次数`”，不再额外显示出刀次数 |
| 13 | 都城近4周 | 官方都城突袭周末成员数据 | 最近 4 个已结束周末的掠夺、出刀和每刀效率 |
| 14 | 竞赛贡献 | 玩家成就 `Games Champion.value` 月度差值 | 最近完成月份积分和近 3 期平均值 |
| 15 | 最近活动 | `last_activity_at` + `last_activity_reason` | 固定为最右侧最后一列；上下两行显示相对时间和依据 |

以下列从成员宽表隐藏：

- 归属人：当前数据基本为空；
- 经验等级：后台仍可用于活动判断，但不展示；
- 所有夜世界字段；
- 历史分：当前计算仍是占位逻辑，业务公式未最终确认，避免产生误导；
- 报名状态：属于联赛报名维度，避免与当前成员状态混淆；
- 最近报名：与成员贡献和活跃判断关系较弱，留给后续联赛报名管理页面；
- 独立成员状态列：默认只展示当前成员，已离开玩家改用筛选和昵称旁灰色标签表达；
- 每行“最近同步”：改为页面工具栏统一显示整批数据更新时间。

“忽略主世界、夜世界奖杯”仅指两者不参与最近活动判断。主世界奖杯保留为展示列，夜世界奖杯不展示。

## 3. 最近数据活动

### 3.1 比较时机

`coc_sync` 每次准备覆盖成员旧 `coc_raw` 前，读取新旧值并比较。出现有效变化时更新：

- `last_activity_at`：本次同步检测到变化的时间；
- `last_activity_reason`：触发本次更新时间的原因；
- `activity_observed_since`：该玩家开始进入本功能观察范围的时间。

没有有效变化时照常覆盖 `coc_raw`，但保留原 `last_activity_at`。第一版不保存完整成员快照历史，也不新增通用活动事件表。

`last_activity_at` 是“检测时间”，不是数据实际发生变化的精确时间。成员同步维持当前 6 小时周期时，其时间精度约为 6 小时。

### 3.2 有效变化白名单

| 中文含义 | API 字段 | 有效变化 | 活动原因文案 |
|---|---|---|---|
| 赛季捐兵 | `donations` | 新旧都有值且新值大于旧值 | 捐兵增加 |
| 赛季收兵 | `donationsReceived` | 新旧都有值且新值大于旧值 | 收兵增加 |
| 经验等级 | `expLevel` | 新旧都有值且新值大于旧值 | 经验等级提升 |
| 大本营等级 | `townHallLevel` | 新旧都有值且新值大于旧值 | 大本营升级 |
| 玩家昵称 | `name` | 新旧都有值且内容不同 | 昵称变化 |
| 玩家小屋 | `playerHouse` | 规范化后新旧内容不同 | 玩家小屋变化 |
| 赛季进攻胜场 | 玩家详情 `attackWins` | 新旧都有值且新值大于旧值 | 赛季进攻增加 |
| 普通部落战进攻 | `current_war_cache` | 与覆盖前缓存相比出现该玩家的新进攻 | 普通战进攻 |
| CWL 进攻 | `cwl_live_war_cache` | 与覆盖前缓存相比出现该玩家的新进攻 | 联赛进攻 |

同一次同步命中多项变化时，可以按固定顺序合并原因，例如“捐兵增加、赛季进攻增加”。

### 3.3 明确忽略的变化

以下变化不得更新最近活动时间：

- 主世界奖杯 `trophies`；
- 夜世界奖杯 `builderBaseTrophies`；
- 当前和上次部落排名 `clanRank`、`previousClanRank`；
- 联赛段位 `league`、`leagueTier`；
- 部落职位 `role`；
- 所在部落 `clan_tag`。

原因包括赛季自动变化、其他玩家间接影响、离线防守和管理员操作。这些变化不能可靠证明玩家本人有活动。

### 3.4 赛季重置与初始值

赛季累计字段只认增加，不认减少：

```text
捐兵 0 -> 20       有效活动
捐兵 500 -> 0      忽略，可能为赛季重置
赛季进攻 30 -> 0   忽略，可能为赛季重置
```

还需遵守：

- 字段从有值变为空值，不算活动；
- 旧快照没有字段、新快照首次出现字段，不算活动，避免 API 结构变化误判；
- 玩家首次进入观察范围时只写 `activity_observed_since`，不把首次同步时间当作活动时间；
- 现有成员上线该功能时不回填虚假的历史活动时间；
- 尚未检测到活动时显示“自 YYYY-MM-DD 开始观察，暂未检测到活动”。

玩家详情接口返回的部落标签可能把历史配置中的字母 `O` 规范为数字 `0`。判断 `membership_status` 时必须把两者视作同一 COC 标签，并继续保存配置中的标签拼写，避免成员详情刷新把仍在自有部落的玩家误判为“已离开”，也避免破坏现有缓存和筛选键。

## 4. 战斗表现摘要

### 4.1 普战近15战

成员主表按 `player_tag` 跨全部自有部落聚合。先限定最近 90 天内已结束的普通战，再取该玩家实际上阵的最近最多 15 场；玩家在自有部落之间转移时，历史记录连续累计，不以当前 `accounts.clan_tag` 切断。当前部落只用于列表展示、筛选和概览，不是历史战绩边界。

“自有部落”是硬边界，“部落类型”不是过滤条件：战营、混营、互刷、偷矿、壳子等只要在战争发生时由系统以自有部落身份采集，均可计入；玩家代表外部部落参加的战争不计入。CWL 不进入普通战窗口。

显示格式：

```text
三星 60% · 9/15
出刀 83% · 15/18
```

- 三星率 = 有效三星次数 / 实际进攻次数；
- 出刀率 = 实际进攻次数 / 该玩家上阵战争中的可用进攻次数；
- 每场可用进攻次数读取战争自身的 `attacks_per_member`，不得写死为 2；
- 玩家已进入一场战争阵容但没有出刀时，该场仍计入可用进攻次数；
- 普通战继续遵守“部落达到满星前”的既有有效进攻口径；
- 90 天内不足 15 场时使用已有全部参战战争，并显示真实样本；
- 90 天内没有参战或实际进攻样本时显示 `-`，不能用更早的历史战绩补足 15 场，也不能显示为 `0%`。

### 4.2 联赛近3月

联赛列统计最近 3 个完整联赛月：

```text
三星 43% · 6/14
出刀 14次
```

- 三星率 = 进攻三星次数 / 实际进攻次数；
- 按 `player_tag` 汇总最近 3 个完整联赛月内全部自有联赛队伍的记录，不受玩家当前部落限制；
- 自有联赛队伍以对应月份的 `league_teams` 历史快照为准，不限制 `combat`、`shell` 或其他业务分类；
- 联赛轮换成员只有实际进入当日阵容才有出刀机会，第一版不以“3 个月 × 7 场”构造虚假的应出刀数；
- 未参加联赛或窗口内没有进攻记录时显示 `-`，与“进攻过但 0 次三星”严格区分。

成员主表不增加普通战或联赛防守三星率。防守表现受大本、阵型和对手强度影响，继续放在战营/联赛详情页。

### 4.3 计算成本与缓存边界

普通战摘要读取全部自有部落的本地战争事实；联赛摘要读取结构化 `league_results` 和对应月份的 `league_teams`。两者都使用本地数据，页面请求不新增 COC API 调用。自有部落边界按战争发生时保存的部落标签或月度队伍快照确定，不能拿玩家当前部落反推历史归属。

`war_history_cache` 当前每个部落只保留最近 15 场完整 JSON，不能单独保证“玩家最近 90 天最多 15 场”的跨部落窗口。实施时必须在完整战争被清理前固化玩家上阵、可用刀数、实际进攻和三星等可重建事实；不能因某个部落完成第 16 场战争而丢失仍处于 90 天窗口内的玩家记录。

2026-10-02 的容量核对为：407 名当前成员、166 场普通战缓存（约 7.4 MB）、937 行联赛记录。一次解析全部普通战 JSON 约 115 ms，直接计算可以运行，但没有必要在每次页面请求重复解析。当前实现按数据变化增量预计算：

- `current_wars` 归档普通战时先固化该场玩家事实；仅在状态进入 `war_ended` 且事实新增或变化时，才按受影响的 `player_tag` 跨全部自有部落重算；进行中战争只更新当前战缓存和活动观察；
- `league_results` 更新后，只重算受影响月份和玩家；
- 每日执行一次窗口过期检查，使超过 90 天的普通战和不再属于最近 3 个完整月的联赛记录及时退出汇总；
- `/api/members` 只联结轻量汇总，不读取完整战争 JSON，也不现场访问 COC；
- 同步或重算失败保留上次成功汇总并标记更新时间。

赛季进攻 `attackWins` 与上述本地战绩不同，需要逐玩家读取官方详情，是成员页设计中主要的额外 API 成本，必须独立限频和缓存。

## 5. 都城与竞赛贡献

### 5.1 都城近4周

官方 `/clans/{clanTag}/capitalraidseasons` 的成员数据包含 `attacks`、`attackLimit`、`bonusAttackLimit` 和 `capitalResourcesLooted`。成员主表汇总最近 4 个已结束突袭周末：

```text
掠夺 320K
出刀 23/24 · 均13.9K
```

- 总掠夺 = `capitalResourcesLooted` 累加；
- 总出刀 = `attacks` 累加；
- 可用刀数 = `attackLimit + bonusAttackLimit` 累加；
- 每刀掠夺 = 总掠夺 / 总出刀；
- 排序优先使用总掠夺，每刀效率只作辅助；收尾残血区域会降低单刀掠夺，不能把效率单独解释为绝对能力；
- 没有成员级样本时显示 `-`。

玩家详情的 `clanCapitalContributions` 是长期累计建设投入，受入部时间影响，不进入成员主表；后续可放在单玩家详情。

统计任务按北京时间每周二 03:00 执行。突袭周末在周一 15:00 结束，留出 12 小时等待官方结果稳定。每个部落读取最近若干期并按 `clan_tag + startTime` 幂等补齐，不能只取最新一条，否则停机一周会永久漏数。常规成本约为 12 个自有部落每周 12 次请求。

### 5.2 竞赛贡献

官方没有直接返回“本期部落竞赛积分”，但玩家详情成就 `Games Champion.value` 保存历史累计竞赛积分。每月结束快照与上月结束快照相减，得到本期增量：

```text
9月 4000
近3期均 3267
```

- 本期积分 = 本月结束累计值 - 上月结束累计值；
- 近 3 期平均只使用状态完整的月度结果，并显示实际已有期数；
- 首次部署没有上月基准时只保存基准，不将累计总值误作本期积分；
- 新成员或缺少基准时显示“记录不完整”，不能显示 0；
- 竞赛积分归属玩家开始第一个挑战时所在部落；如果只做玩家贡献展示，可以按玩家标签保留积分，不能据月末所在部落反推历史部落归属。

统计任务按北京时间每月 29 日 03:00 执行。常规竞赛在 28 日 16:00 结束，留出 11 小时等待结果稳定。任务逐个读取当前成员玩家详情；该响应同时包含已规划的 `attackWins`，应复用一次请求。按当前约 407 名成员计算，每月约 407 次请求。

首次上线且日期早于当月 22 日时，可强制执行一次竞赛任务，将当前累计值记作上月结束基准；该基准本身标记不完整，但足以供本月 29 日计算完整差值。竞赛开始后至结果窗口前拒绝建立基准。

都城和竞赛均只做结束后汇总，不在活动期间高频刷新。都城任务失败后每 6 小时重试至周三结束；竞赛任务失败后每 6 小时重试至 30 日结束。重试幂等，失败保留上次成功数据。

## 6. 数据库与 API 实现

`accounts` 已增加：

| 字段 | 类型 | 说明 |
|---|---|---|
| `season_attack_wins` | INTEGER | 玩家详情接口返回的当前赛季进攻胜场 |
| `last_activity_at` | TEXT | 最近一次检测到有效变化的 UTC ISO 时间 |
| `last_activity_reason` | TEXT | 本次有效变化原因；多项按固定顺序合并 |
| `activity_observed_since` | TEXT | 开始观察该玩家的 UTC ISO 时间 |

普通战逐玩家事实先写入 `member_war_facts`，以 `(clan_tag, war_key, player_tag)` 唯一；战斗摘要再写入可重建的 `member_combat_stats_cache`，以 `player_tag` 为主键。玩家当前 `clan_tag` 只作为展示信息保留在 `accounts`，不作为缓存统计范围。缓存保存计数和窗口身份，不只保存百分比：

| 字段组 | 内容 |
|---|---|
| 普通战窗口 | 90 天起止时间、实际纳入的战争身份和自有部落标签、战争数、三星数、实际进攻数、可用进攻数 |
| 联赛窗口 | 3 个完整月份标识、实际纳入的自有联赛队伍标签、三星数、实际进攻数 |
| 缓存状态 | `updated_at`、状态和错误信息；失败保留上次成功值 |

百分比由 API 使用计数计算，避免舍入值成为新的事实源。玩家转入其他自有部落不会清空或重置历史窗口；只有新的战争事实、时间窗口滑动或自有部落历史边界修正才触发对应统计变化。

都城与竞赛分别保存可追溯事实：

| 表 | 唯一键 | 核心字段 |
|---|---|---|
| `capital_raid_member_results` | `(clan_tag, start_time, player_tag)` | 结束时间、出刀、基础/额外刀数、掠夺都城金币、抓取时间 |
| `clan_games_member_snapshots` | `(period, player_tag)` | 月末累计成就值、本期差值、快照时部落、完整性状态、抓取时间 |

两张表保存周/月事实，成员页的近 4 周与近 3 期值在任务完成后生成轻量汇总或查询缓存。历史事实不得因成员退部或换部落被覆盖。

## 7. 页面交互

- 表格固定为上述 15 列，继续支持横向滚动，表头和单元格固定宽度；筛选和排序针对完整结果集，但每页只渲染 100 人，切换条件后回到第 1 页，避免“全部成员”一次生成上万个小程序节点；
- 最近活动固定为最右侧最后一列；
- “最近活动”单元格第一行显示“2天前”等相对时间，第二行显示原因；
- 页面顶部统一显示最近一批成员数据更新时间；
- 默认只展示 `membership_status = 'member'` 的当前成员；成员状态筛选提供“在部落 / 已离开 / 全部”，选择“已离开”或“全部”时，在离开玩家昵称旁显示灰色“已离开”标签，不增加独立状态列；
- 部落筛选继续支持自有部落多选；
- 搜索覆盖昵称、玩家标签和部落标签；
- 可排序字段至少包括大本、奖杯、赛季进攻、赛季捐兵、赛季收兵、最近活动、部落战近15场、联赛近3月、都城近4周和竞赛贡献；无样本项排在有样本项之后。

第一版只展示“多久未检测到活动”，不自动标记“死鱼”。14 天、30 天或组合阈值需等数据积累后再确认。

## 8. 实施验收

- 赛季重置造成的累计值下降不会刷新活动时间；
- 奖杯、排名、联赛、职位和部落归属变化不会刷新活动时间；
- 有效字段增加后只更新对应玩家，其他玩家不受影响；
- 同步失败不会清空旧活动时间、原因或赛季进攻缓存；
- 首次同步只开始观察，不伪造活动记录；
- API 和页面都明确使用“最近数据活动”，不出现“上次登录”；
- 战斗百分比始终同时显示三星数和实际进攻样本；无样本显示 `-`，真实零三星显示 `0%`；
- 普通战限制最近 90 天并按玩家跨全部自有部落取最近最多 15 场，联赛按玩家跨全部自有联赛队伍使用最近 3 个完整月；
- 两项统计都必须限制在自有部落边界内，但不按战营、混营、互刷、偷矿、`combat` 或 `shell` 等类型过滤；
- 成员页读取预计算汇总，不在请求中解析全部战争 JSON 或调用官方 API；
- 都城每周二 03:00 汇总上一个已结束周末，漏跑后能按周末身份补齐；
- 竞赛每月 29 日 03:00 保存月末累计值并与上期做差，无基准时标记不完整；
- 都城和竞赛失败重试不清空旧事实或生成重复记录；
- 表格在微信开发者工具和真机中保持横向滚动、列宽和双行活动信息正常。
