# 部落战阵型自动采集与发布：设计问题

> 状态：讨论中（仅设计，不包含实现代码）
>
> 第一期目标：每天从 X（原 Twitter）关注的作者帖子中发现《部落冲突》阵型，整理为公众号可发布的图文内容；抖音发布暂不实现，但保留扩展边界。

## 1. 已知目标与示例

- 输入：X 上指定作者的帖子（可能包含多张阵型截图、`link.clashofclans.com` 阵型链接，以及说明文字）。
- 产物：每个阵型一张图片、一个可点击链接，以及可供公众号编辑/发布的文章素材。
- 运行方式：每日定时执行，支持重复执行不重复发布。
- 第一阶段发布渠道：微信公众号；抖音作为后续渠道。
- 图片默认理解为作者帖子中的阵型截图（示例见需求附件），是否需要裁剪、加水印、统一标题待确认。

## 2. 需要先确认的业务问题

### 2.1 来源与筛选

1. ~~“关注的作者”是读取某个 X 账号的 following 列表，还是在配置文件中维护作者白名单？~~
   **已确认：**在配置文件中指定固定作者列表，按列表拉取帖子，不读取 following 列表。
2. 是否只处理原创帖，是否排除转发、回复、引用帖和作者自己的评论？
3. 如何判断一张图片是阵型图（人工审核、关键词/链接规则，还是视觉模型）？
4. 需要采集哪些大本营/模式：普通村、主世界/夜世界、部落战/CWL、不同 TH 等？
5. 每天采集的时间窗和时区是什么？历史帖子补采范围多大？
6. X API 计划使用哪种授权方式和套餐？是否接受官方 API 的配额、费用与速率限制？

### 2.2 内容与归属

1. ~~是否已获得作者转载/商用授权？公众号文章中需要展示作者名、X 原帖链接和版权声明吗？~~
   **已确认：**默认具有转载权限；仍建议保留作者名和 X 原帖链接，版权声明格式待定。
2. 阵型图片是否允许保存到本地/对象存储并二次加工？保存多久？
3. 发现同一阵型被多位作者发布时，按链接、图片哈希还是人工规则去重？
4. 文章标题、摘要、正文模板、语言（中文/英文）和排序规则是什么？
5. ~~一个帖子有多个阵型时，是否拆成多条“每阵型一图一链接”，还是合并为一篇文章？每天最多发布几篇？~~
   **已确认：**多个作者的帖子按增量窗口汇总为一篇公众号草稿，每位作者最多整理最新 5 个帖子；每个阵型依次放截图、阵型链接，阵型之间插入空白行。
6. ~~文章标题和封面如何生成？~~
   **已确认：**标题格式为“冲杯阵 + 日期”（日期格式待实现时统一）；封面使用该文章第一个阵型的图片。

### 2.3 阵型链接与图片处理

1. 仅接受官方 `link.clashofclans.com` 深链接，还是允许第三方链接？是否需要验证链接可打开、解析出模式/TH？
2. 图片来源是 X 原图还是帖子视频/外链截图？最低分辨率、格式和大小限制是什么？
3. 是否自动裁剪拼图、去除 X 界面、叠加中文标签/作者水印？
4. 图片存放位置：本地 `data/`、腾讯云 COS，还是公众号素材库？
   **已确认实现约定：**运行时图片默认保存到仓库外的 `/tmp/sky-admin-war-layout`，可用 `WAR_LAYOUT_MEDIA_DIR` 覆盖；测试数据库默认保存到 `modules/war_layout/runtime/war_layout.db`，可用 `WAR_LAYOUT_DB_PATH` 覆盖；图片和数据库均不纳入 Git。

### 2.4 公众号发布流程

1. ~~发布方式是“自动创建草稿，人工审核后群发”，还是直接自动群发？（建议第一期采用前者。）~~
   **已确认：**第一版只验证自动创建草稿功能，不自动群发。
2. 使用哪个公众号、谁提供 AppID/AppSecret？凭据必须放环境变量，不进入配置和日志。
3. 是否需要图文封面、作者、原文链接、留言/赞赏等字段？
4. 发布失败是否重试，失败后是否告警（企业微信、邮件或日志）？
5. 如何记录发布状态和微信 media_id，保证重跑幂等？

### 2.5 运营与审核

1. 是否需要后台审核队列（可编辑、删除、标记已发布），还是先生成 Markdown/HTML 供人工复制？
2. 违规内容、失效链接和低质量图片由谁审核？是否需要黑名单作者/关键词？
3. 统计需求：采集数、去重数、草稿数、发布数、失败原因、点击/阅读数据是否需要保存？

## 3. 建议的第一期边界（待确认）

建议先实现“采集 + 规范化 + 草稿”，不直接群发：

1. 配置作者白名单、采集时间窗和发布模板。
2. 通过 X 官方 API 拉取帖子，保存原始元数据，下载并校验图片。
3. 提取官方阵型链接，生成稳定指纹并去重。
4. 产出每阵型一条记录（作者、原帖、图片、阵型链接、识别标签、审核状态）。
5. 调用微信公众号接口上传图片并创建草稿；人工确认后再群发。标题使用“冲杯阵 + 日期”，封面使用第一个阵型图片；所有帖子汇总最多 5 个阵型，每个阵型按“截图 → 阵型链接”顺序排版，阵型之间使用空白行分隔。
6. 使用现有 scheduler 的持久化任务机制，不新增独立 cron/旧 timer 体系。

### 当前运行配置约定

- X 作者列表：根目录 `.env` 的 `WAR_LAYOUT_X_AUTHORS`，当前配置为 3 位指定作者。
- X Token：根目录 `.env` 的 `X_BEARER_TOKEN`；不得写入代码或提交 Git。
- 数据源：`WAR_LAYOUT_SOURCE=official`（默认）或 `socialdata`；启用 SocialData 时使用 `SOCIALDATA_API_KEY`，仅走 `SocialDataSource` 的 Data API 安全限制。
- SocialData 作者 ID：使用 `WAR_LAYOUT_X_USER_IDS=name=id,name2=id2` 持久化映射；启用 SocialData 时必须为所有作者配置，避免每轮额外消耗用户资料请求。
- 测试数据库：`modules/war_layout/runtime/war_layout.db`，可由 `WAR_LAYOUT_DB_PATH` 覆盖。
- 图片素材：默认 `/tmp/sky-admin-war-layout`，可由 `WAR_LAYOUT_MEDIA_DIR` 覆盖。
- `modules/war_layout/.gitignore` 已忽略 `runtime/`、数据库和图片扩展名。

### 帖子筛选规则

作者的普通动态会被拉取但不会进入草稿：只有包含官方 `link.clashofclans.com` 阵型链接并能与图片配对的候选才会保留。多个作者按返回顺序合并，最终全局取前 5 个阵型。

### 下一步

先由有终端权限的人员执行真实 X 只读 smoke test，确认作者用户名、API 权限和实际帖子格式；根据输出再调整图片/链接筛选。确认无误后，才进行真实图片下载和测试公众号草稿验证。暂不接入每日 scheduler。

### SocialData 使用限制（低余额保护）

SocialData 官方 Fair-use 规则是每分钟最多 3 次请求不扣费；超过后按正常价格计费。代码已提供 `SocialDataBudgetGuard` 和 `SocialDataSource`，默认在第 4 次请求前直接抛出异常；适配器只允许调用 Data API，禁止 Monitoring API。

- 使用限速器，任意连续 60 秒最多发出 3 次请求；
- 缓存作者用户 ID，避免重复查询资料；
- 默认每位作者只读取一页，不自动翻页；
- 禁止并发请求、自动重试和分页追踪，除非明确启用付费模式；
- 收到 `402 Payment Required` 立即停止任务，不继续重试。

当前余额较低，真实测试阶段不再额外调用 SocialData；适配器实现时必须先满足上述限制。

### 每日发布规则

- 所有作者共用一个全局 `last_pull_time` 水位。本次只拉取上次成功同步时间到本次同步开始时间之间的帖子；首次运行默认回看最近 24 小时。
- 每次全作者同步写入一条历史时间戳，记录窗口起止时间、成功/失败状态、帖子数和阵型数；最新成功时间用于下一次增量拉取。
- 每次运行按作者分别取最新的最多 5 个帖子，超出的帖子直接丢弃；随后在同一篇草稿中一次发布本次各作者保留的全部新阵型，不建立长期缓冲队列。
- 所有作者合计没有新阵型时不创建草稿；已经创建草稿的记录通过帖子/阵型指纹跳过。
- 所有作者请求和草稿处理成功后才推进全局同步水位；任一环节失败时保留旧水位，下一次继续补抓。
- 同步窗口使用 UTC 时间和帖子 ID 去重，不能依赖自然日边界；`--date` 仅用于覆盖草稿标题日期。
- 草稿成功后标记 `draft_created`；失败标记 `failed`，下次优先重试。
- 已创建草稿的记录默认跳过；仅显式使用 `--force` 时重新创建。

### 图片与链接配对规则（已确认）

- 只接受官方 `link.clashofclans.com` 阵型链接；Discord 等其他链接全部丢弃，不参与配对和文章正文。
- 一个帖子只有一个阵型链接、但有多张图片时，视为一个阵型的一对多关系：保留全部图片，正文按“全部图片 → 一个阵型链接 → 来源”展示。
- 一个帖子有多个阵型链接和多张图片时，默认按顺序一对一配对。
- 图片多于阵型链接时，多出的图片归入最后一个阵型链接。
- 图片少于阵型链接时，超出图片数量的链接丢弃；没有图片的链接不进入草稿。
- 一个帖子（无论包含几张图片和几个链接）只占该作者每日 5 个帖子名额中的 1 个名额。
- 链接正文显示完整 URL，并使用 HTML `<a href>` 包装；后台草稿编辑器可能仅显示文本，是否可点击以微信手机预览或正式发布结果为准，当前不额外改写为短链接。
- 链接行使用内联 `text-align:left`，避免微信公众号默认两端对齐导致“阵型链接”中文字间距异常。
