# 阵型采集与公众号草稿：渐进式实施计划

> 原则：每一步先完成最小实现和针对性测试，再进入下一步；任何一步失败都不影响现有 CWL、战争统计和调度任务。

## 阶段 0：设计冻结与运行边界

目标：把已确认规则转成可执行的配置和验收样例。

- 固定 X 作者白名单（配置文件，不自动读取 following）。
- 明确文章标题为“冲杯阵 + 日期”，封面取第一个阵型图片。
- 所有作者按增量水位拉取帖子，每位作者最多取最新 5 个帖子；每个阵型为“截图 + 阵型链接”；阵型之间空一行。
- 第一版只创建微信公众号草稿，不自动群发。
- 确认 X API、微信公众号账号、时区、日期格式和凭据注入方式。

测试/验收：用需求附件建立一份脱机 fixture，人工确认预期抽取 5 个阵型及排版结果。

状态：已完成。

## 阶段 1：模块骨架与纯函数解析

目标：创建 `modules/war_layout/` Python 包，仅处理输入数据，不访问网络或数据库。

建议内容：

- 帖子、阵型、图片和链接的数据结构；
- 从帖子文本/媒体元数据提取官方阵型链接；
- 按作者分别截取最多 5 个帖子，超出部分丢弃；
- 生成标题、正文片段和封面选择结果；
- 链接规范化、基础校验和稳定指纹。

测试/验收：覆盖无链接、多链接、重复链接、超过 5 个、缺图和异常文本；测试必须完全离线。

状态：已完成，纯函数测试和无关帖子跳过测试已通过。

## 阶段 2：持久化与幂等记录

目标：增加阵型采集记录和处理状态，保证每日重跑不会重复处理。

- 设计独立表（原始帖子、阵型指纹、图片路径、审核状态、草稿 media_id、错误信息、时间戳）。
- 通过共享 `Database` 连接和 repository 访问；不修改 `accounts` 等现有领域表。
- 明确状态流转：discovered → normalized → draft_created / failed。

测试/验收：重复插入同一帖子和阵型不会产生重复记录；事务回滚、唯一约束和失败重试有测试。

状态：已完成，包含草稿创建幂等测试。

## 阶段 3：X 数据源适配

目标：接入 X 官方 API，按作者白名单和时间窗拉取帖子。

- 凭据只从环境变量/`.env` 读取，日志不得打印 token。
- 实现分页、速率限制、超时和可重试错误处理。
- 先提供 dry-run 命令，将 API 响应转为阶段 1 的标准输入，不下载图片、不写公众号。

测试/验收：使用 mock HTTP 响应覆盖分页、限流、空结果和 API 错误；真实 API 仅做一次小范围手工验证。

状态：官方 X 适配器和 SocialData Data API 适配器均已完成，并已接入编排层的数据源选择。
SocialData 启用低余额保护：每 60 秒最多 3 次请求、每位作者只取一页、不自动翻页或重试，余额不足立即停止。

## 阶段 4：图片下载与素材整理

目标：下载阵型图片并生成公众号可用素材。

- 校验 HTTPS、Content-Type、大小和分辨率；拒绝不安全或非图片地址。
- 明确本地临时目录或对象存储的生命周期；保留原图与处理图的关联。
- 如需裁剪/水印，先实现可关闭的独立处理器，不改变原图。
- 运行时素材默认写入仓库外 `/tmp/sky-admin-war-layout`（`WAR_LAYOUT_MEDIA_DIR` 可覆盖），禁止将图片产物提交到 Git。

测试/验收：本地 fixture 覆盖超大文件、错误 MIME、损坏图片、多图帖子和重复图片；产物可被微信接口接受。

## 阶段 5：微信公众号草稿发布器

目标：将一个帖子生成一篇草稿，暂不群发。

- 获取 access token、上传图片素材、创建草稿；凭据和响应中的敏感字段脱敏。
- 标题按“冲杯阵 + 日期”生成，封面使用第一个阵型图片。
- 正文严格按“图片 → 阵型链接”，阵型之间空白行；每位作者最多 5 个帖子。
- 成功写入 media_id 和状态；失败保留可重试信息。

测试/验收：使用 mock 微信 API 验证请求体、图片顺序、标题、封面和幂等；在测试公众号手工创建一篇草稿并检查展示效果。

状态：mock 验证已完成；测试公众号验证待执行。

## 阶段 6：单次编排命令

目标：串联抓取、解析、素材处理和草稿创建，提供可观测的 dry-run/execute 模式。

- `dry-run` 只读取并输出摘要；`execute` 才写库和创建草稿。
- 每次运行输出作者、帖子数、阵型数、跳过数、成功/失败数，不输出密钥。
- 使用所有作者共用的全局 `last_pull_time` 增量水位；`--date` 仅覆盖草稿标题日期，帖子按帖子时间窗口筛选。

测试/验收：端到端 mock 测试；中途失败后重跑只处理未完成项。

状态：已完成。真实执行入口暂不接 scheduler，使用 `test_x_live.py` 做单页只读验证。

阶段 6 已提供本地 dry-run 入口：

```bash
venv/bin/python -m modules.war_layout.cli \
  --fixture modules/war_layout/fixtures/sample_posts.json
```

该命令只读取 fixture 并输出 JSON，不会下载图片、写数据库或调用微信。

## 阶段 7：接入现有 scheduler

目标：每天定时执行并持久化任务状态。

- 使用 `scripts/scheduler.py` 的现有任务机制，不新增 cron 或旧 timer。
- 默认先以 dry-run 或“只建草稿”模式运行，时间窗和时区来自配置。
- 增加失败告警和运行统计；连续失败不影响其他同步任务。

测试/验收：在非生产环境触发一次调度，检查 `sync_jobs` 状态、日志和重复执行行为；确认 systemd 服务配置前先评审。

已提供待接入的调度器函数：`modules.war_layout.scheduler_job.run_job`。现有调度器接入时只需传入已创建的 service 和设置对象；函数返回 `status/posts/layouts/discovered/skipped` 等可序列化字段，并隐藏异常细节。

## SocialData 正式启用前检查

根目录 `.env` 可设置 `WAR_LAYOUT_SOURCE=socialdata` 和 `SOCIALDATA_API_KEY`。为避免每轮调用用户资料接口产生额外费用，必须同时配置所有作者的数字 ID：

```text
WAR_LAYOUT_X_USER_IDS=author1=123,author2=456
```

缺少任一作者 ID 时配置校验会失败并停止任务；不会降级为额外的资料查询。当前低余额环境不执行真实请求，先使用 mock 测试确认编排结果。
